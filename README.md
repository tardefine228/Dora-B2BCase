# Dora B2BCase — Backend API

Бэкенд на **FastAPI** для классификации товаров по **Постановлению
Правительства РФ № 1875** (национальный режим в закупках): по названию товара
сервис находит вероятную позицию перечня и код ОКПД2, показывает уверенность и
альтернативы. Результат — **подсказка для специалиста**, не юридическая проверка.

## Стек

| Компонент | Технология | Роль |
| --- | --- | --- |
| API | FastAPI | `/classify`, пакетная обработка, админ-эндпоинты, UI на `/ui/` |
| Интерфейс | React + TypeScript + Vite | одиночный товар, загрузка списка, прогресс, экспорт |
| БД | **PostgreSQL** | фоновые задачи и результаты батчей, журнал классификаций (`classification_log`) |
| Очередь | **Celery + Redis** | тяжёлые пакеты обрабатывает отдельный воркер, API не блокируется |
| Векторный поиск | **Qdrant** + эмбеддинги (multilingual-e5 → векторы spaCy → TF-IDF) | кандидаты «по смыслу» + признаки реранкера |
| Реранкер | логистическая модель с калибровкой | порядок кандидатов, уверенность, статусы `ok`/`review`/`not_found` |

**Windows + Docker Desktop: подробная пошаговая инструкция — [`docs/START_WINDOWS_DOCKER.md`](docs/START_WINDOWS_DOCKER.md).**

## Запуск через Docker (рекомендуемый)

```bash
docker compose up --build
```

Поднимаются `api`, `worker` (Celery), `postgres`, `redis`, `qdrant`. Первая сборка долгая
(PyTorch + модель эмбеддингов + обучение реранкера под неё, ~10–15 минут). Повторный
`docker compose up --build` идёт из кэша: слой с загрузками стоит **до** копирования кода
и опирается только на файлы требований, поэтому правки кода/UI не вызывают повторных
загрузок, а pip- и Hugging Face-кэши лежат в BuildKit cache-mount'ах. Обычный
`docker compose up` (без `--build`) не скачивает ничего и стартует за секунды;
векторный кэш каталога и коллекции Qdrant переживают рестарт в volumes.

- UI/API:  http://localhost:8000/ui/  ·  Swagger: http://localhost:8000/docs
- Что реально работает: `curl localhost:8000/health/ready` → блок `vector_search`
  (`embedder`, `dim`, `store` = `qdrant`/`memory`, `reranker` — какой артефакт скорит,
  `scoring`), `job_store`, `queue_backend`.
- Без трансформера (быстрая сборка, ~2 мин): `INSTALL_TRANSFORMER=false docker compose up --build` —
  векторный слой работает на офлайн-векторах spaCy.
- Если скачивание модели при сборке не удалось, сборка **не падает**: сервис откатывается на
  spaCy, а `/health/ready` покажет `embedder: spacy-ru_core_news_md`.
- Тот же шаг обучает векторный реранкер и **допускает его гейтом** (метрики по строкам + ECE).
  Если гейт отклонил артефакт, в образе остаётся `reranker.json` и в логе старта будет
  «Нет реранкера для эмбеддера … используем лексический»: векторный поиск тогда только
  пополняет кандидатов, но не скорит. Вердикт с числами лежит в образе —
  `/app/ml/artifacts/dense-gate.json`; `reranker` в `/health/ready` показывает, какой
  артефакт реально скорит.
- Версия Python-клиента Qdrant закреплена под сервер из `docker-compose.yml`
  (`qdrant/qdrant:v1.14.1` → `qdrant-client>=1.14,<1.15`): при расхождении больше одной minor
  клиент пишет предупреждение и ведёт себя неопределённо. Обновлять их нужно вместе;
  прыжок сервера через несколько minor требует снапшота тома `qdrant_data`
  (`eval/docker-target-checklist.md`).
- Чтобы трансформер запёкся, сборке нужны исходящие HTTPS на: `huggingface.co` (API и веса),
  `*.hf.co` / `cdn-lfs.hf.co` (CDN весов), `download.pytorch.org` (torch CPU), `pypi.org` и
  `files.pythonhosted.org` (пакеты). Антивирусный веб-фильтр или корпоративный прокси любят
  резать именно их: сборка теперь проверяет доступность Hugging Face **до** тяжёлых скачиваний
  и печатает в лог, какой именно шаг упал. Успех виден так: в логе сборки есть строка
  `Model intfloat/multilingual-e5-small saved to …`, без `WARNING: transformer step failed`,
  а `/health/ready` → `vector_search.embedder` = `st-embedder`, `dim` = 384 (у spaCy —
  `spacy-ru_core_news_md`, `dim` = 300).
- Сборка успешна, но `/health/ready` всё равно показывает `spacy-ru_core_news_md`? Почти
  всегда виноват устаревший `MODEL_NAME` в вашем `.env` (например, `./models/bge-m3` из
  старых ревизий `.env.example`): переменная из `.env` перекрывает путь `/opt/models/embedder`,
  запечённый в образе, каталог не находится — и рантайм молча откатывается на spaCy.
  Диагностика: `docker compose exec api ls /opt/models/embedder` (модель в образе есть?)
  и `docker compose exec api printenv MODEL_NAME` (что реально видит сервис?). Лечение —
  убрать строку `MODEL_NAME` из `.env` и `docker compose up -d`; пересборка не нужна.
  Первый старт после переключения займёт минуту-другую: каталог переэмбедится заново
  (кэш векторов и коллекция-зеркало в Qdrant именуются по тегу эмбеддера, поэтому
  старые векторы не переиспользуются и удаляются автоматически).
- Другая модель эмбеддингов (например `BAAI/bge-m3`, 1024 измерения) ставится build-arg'ом:
  `EMBEDDER_MODEL=BAAI/bge-m3 docker compose build`. Что учесть: 568M параметров требуют
  **4 ГБ** на `api` и `worker` (`API_MEMORY_LIMIT`/`WORKER_MEMORY_LIMIT`) и
  `MODEL_BATCH_SIZE=4..8`; реранкер нужно пересобрать под новый эмбеддер
  (`scripts/build_model.py --dense --gate`), иначе векторные признаки останутся с весом 0.
  Разбор готовности, ограничений и порядка шагов — [`docs/bge-m3-readiness.md`](docs/bge-m3-readiness.md).

Проверка стека на целевой машине: `bash scripts/docker_smoke.sh --build`.

## Быстрый старт (локально, без Docker)

```bash
python -m pip install -r api/requirements-dev.txt
PYTHONPATH=api uvicorn app.main:app --reload --port 8000 --no-proxy-headers
```

По умолчанию локально: задачи в SQLite (`JOB_STORE=sqlite`), пакеты в процессе API
(`QUEUE_BACKEND=inprocess`), векторы в памяти (`VECTOR_STORE=memory`). Полный стек —
переменными окружения (см. таблицу ниже) и сервисами из `docker-compose.yml`.

## Векторный поиск

Классификатор в режиме `catalog` — **гибридный**: шорт-лист = лексический матчер ∪ ближайшие
по смыслу позиции из векторного индекса (`ml/dense.py`). Векторы названий позиций строятся
выбранным эмбеддером (`EMBEDDER_BACKEND=auto`: sentence-transformers → spaCy → TF-IDF),
публикуются в Qdrant (коллекция адресуется содержимым каталога: новый каталог = новая
коллекция, старая удаляется) и кэшируются на диске. Ближайших соседей отдаёт Qdrant;
при его недоступности поиск автоматически идёт по матрице в памяти.

Косинус «запрос ↔ кандидат» — признак реранкера. Шкалы косинусов у разных эмбеддеров разные,
поэтому реранкер с векторными признаками обучается **под конкретный эмбеддер**
(`reranker.<тег-эмбеддера>.json`), а API берёт тот, что соответствует загруженному эмбеддеру —
в **обоих** режимах: `catalog` и `qdrant` (в семантическом косинус попадает в `dense_cosine`/
`dense_gap`, иначе признак был бы нулевым и артефакт не влиял бы на решение).
`SEMANTIC_RERANKER=lexical` — откат без пересборки образа: **оба** режима (`catalog` и `qdrant`)
переходят на общий `reranker.json`, а векторный поиск продолжает пополнять кандидатов (иначе
откат заодно снизил бы полноту шорт-листа). Какой артефакт реально скорит, видно в
`GET /health/ready` → `vector_search.reranker` и `vector_search.scoring`; при векторных
признаках пороги `QDRANT_*_FLOOR` надо перемерить под эмбеддер.

**Что скорит по умолчанию.** Когда векторный поиск включён и для активного эмбеддера есть
обученный артефакт, решение принимает он (`reranker.tfidf.json` для tfidf), а `reranker.json` —
запасной вариант для эмбеддеров без своего артефакта. Оба файла и их происхождение описаны в
[`ml/artifacts/README.md`](ml/artifacts/README.md).

**Предохранитель.** Векторные признаки учатся на синтетических запросах и могут ухудшить
реальные ответы. Поэтому `scripts/build_model.py --dense --gate` оценивает такой реранкер на
`eval/labeled_examples.csv`: печатает сравнение **по строкам** (сколько верных ответов из
скольких, а не проценты), пишет отчёт `<models-dir>/dense-gate.json` и **удаляет артефакт,
если тот не прошёл допуск** — тогда вектора только пополняют список кандидатов. Правило
(модуль `eval/dense_gate.py`, 22 теста):

* «верный `not_found`» и точные названия каталога — жёсткие: ни одной строки нельзя потерять;
* top-1/top-3/top-1 по всем — допустима потеря не более одной строки (это шум на 201/233
  оцениваемых строках), и хотя бы одна из них должна выиграть, иначе менять нечего;
* точность статуса `ok` сравнивается по числу **неверных** уверенных ответов (допуск +1
  строка), а не по проценту: знаменатель — это ответы, которые выбрала сама модель;
* ECE не может вырасти больше чем на 0.01.

Один прогон — это одно разбиение обучающих данных, а вердикт от разбиения зависит: с одним и
тем же кодом лексический артефакт отвечал на 93 / 88 / 93 / 89 строк «вне перечня» из 108 при
seed 1875–1878, векторный — на 92 / 91 / 91 / 92 (замер до аудита разметки; после него
проверенных строк «вне перечня» 32, остальные вынесены в `unclear`). При нулевом допуске на тишину это значит,
что гейт решает броском монеты (измерено: один и тот же фикс автокоррекции отклонялся при
seed 1875 и принимался при 1876). Поэтому есть режим `--gate-seeds 1875,1876,1877,1878`:
счётчики прогонов складываются, допуск на строку умножается на их число, а те же правила
применяются к пулу — систематическая потеря тишины остаётся фатальной, разовое колебание нет.
Отчёт несёт `runs`, `seeds` и `decision_basis` (`single_run` / `pooled`).

База для сравнения всегда обучается тем же кодом в том же прогоне: артефакты не
воспроизводятся между версиями тренера, и сравнение с файлом прошлой сборки мерило бы
разные рабочие точки (именно так гейт однажды отклонил артефакт, который был лучше).

Что измерено на размеченном наборе после аудита разметки (201 товар из перечня + 32 проверенных
«вне перечня» + 41 спорная строка, которая не входит в проценты; эмбеддер tfidf,
воспроизводится по seed 1875). Лексическая строка — замер 2026-10-25 после эксп. 36, векторная —
замер 2026-10-24: файл `reranker.tfidf.json` в том прогоне не переобучался, поэтому его числа
относятся к лексике предыдущей волны, а его ECE — ещё и к прежнему правилу калибровки (ниже):

| Вариант | top-1 с кодом | top-3 | тишина | top-1 по всем | ECE |
| --- | ---: | ---: | ---: | ---: | ---: |
| лексика (пересборка текущим кодом) | 95.0% | 98.5% | 96.9% | 95.3% | 0.012 |
| **+ векторные признаки (`ml/artifacts/reranker.tfidf.json`)** | **95.5%** | **99.0%** | **96.9%** | **95.7%** | **0.029** |
| старый `reranker.json` (снят с эксплуатации, эксп. 19) | — | — | — | — | — |

Цифры выросли не из-за смены набора: третья волна мостов лексикона (эксп. 29) и четвёртая
(эксп. 30) научили модель называть 41 позицию её собственным товарным словом («дрель»,
«гантели», «сканер», «флешка» → позиция перечня), а офисную мебель — по предмету, а не по
модификатору «офисный». Пятая волна (эксп. 34) добавила 19 мостов на омонимы реальных закупок
(«кабель», «кран», «портландцемент») и правило слабой подсказки: строка со спецификаторами, у
которой головное слово написано в названии позиции, теперь показывается как `review`, а не как
пустая строка — на трёх выгрузках по 100 строк пустых ответов стало 68 вместо 115. Шестая волна
(эксп. 35) закрыла товары, которые в перечне есть, но названы официально («манометр» →
«приборы для измерения давления», «реле» → «устройства коммутации или защиты цепей»,
«маршрутизатор» → «средства связи, выполняющие функцию систем коммутации»): пустых стало 53 из
300. Седьмая волна (эксп. 36) закрыла последние два вопроса разметки — ИБП («источник
бесперебойного питания» → блоки вычислительных машин) и датчик температуры (только при
температурном контексте, иначе молчание): пустых 49 из 300, уверенных `ok` 201 вместо 173.
Спорные строки (41) по-прежнему не входят в проценты (`docs/labeling-doctrine.md`).

Показная шкала уверенности после эксп. 36 честно может быть равна сырой: Platt-карта надевается
только если её сдвиг больше собственной ошибки калибровочной площадки (`CALIBRATION_SHIFT_SIGMAS`
в `ml/train_reranker.py`). Раньше карта подбиралась всегда, и её интерсепт на насыщенной площадке
определял сид разбиения — при неизменном top-1 ECE гулял от 0.018 до 0.036. Теперь гулять нечему:
0.012, и это число воспроизводится (`meta.calibration_platform` в артефакте хранит сдвиг, его
ошибку и решение).

Векторный артефакт проходит гейт по пулу четырёх прогонов: +7 строк top-1, +14 top-3,
+4 верной тишины, 5 неверных `ok` вместо 26, ECE в допуске (0.032 → 0.039 при пороге +0.01).
Отрицательный контроль (те же веса с обнулёнными `dense_*`) отклоняется и удаляется — гейт не
«пропускает всё». Он подхватывается, когда активен эмбеддер `tfidf`; для трансформера артефакт
строится при сборке образа тем же шагом `--gate`.

Старый лексический файл, который не воспроизводился текущим тренером (29277 пар, пороги
0.621/0.097, ECE 0.102), снят с эксплуатации: его 87.3 % top-1 были следствием более низкого
порога, а не лучшего ранжирования — при равной тишине 85 % он проигрывает 5 строк
(`eval/experiments.md`, эксп. 18–19). На его место отгружена воспроизводимая пересборка
(`ml/artifacts/reranker.json`, текущий sha256 — в таблице `ml/artifacts/README.md`), которая и
служит откатом (`SEMANTIC_RERANKER=lexical`).

## Режимы классификации (`CLASSIFIER_BACKEND`)

| Значение | Что делает | Когда использовать |
| --- | --- | --- |
| `catalog` | реальный каталог `data/data.csv`: гибридная выдача (лексика + векторный поиск) + обученный реранкер + откалиброванные пороги (**по умолчанию**) | основной режим |
| `qdrant` | чисто семантический поиск в Qdrant (`ml/`), тот же реранкер, свои пороги | эксперименты со сравнением режимов |
| `mock` | детерминированная заглушка `MOCK-001` | разработка фронтенда |

**Выбор режима для демо:** каталоговый гибрид работает офлайн и на текущих артефактах даёт
top-1 95.5% (top-3 99.0%) по товарам из перечня и 96.9% верной тишины на проверенных строках
(`eval/eval_report.md`); откат на `SEMANTIC_RERANKER=lexical` даёт 95.0% / 98.5% / 96.9%.
Семантический режим измерен на том же наборе и настроен отдельно (эксп. 15–16, 28, 29,
`eval/backend_comparison.md`, `eval/eval_report_qdrant.md`): на своей рабочей точке
(`review = 0.45`) он даёт top-1 68.7% и 90.6% верной тишины — то есть и отвечает реже, и
ошибается чаще каталога, — и стоит вчетверо дороже (p50 ~171 мс против ~39 мс). Поэтому
**по умолчанию остаётся `catalog`**, а `qdrant` включается флагом как экспериментальный режим. Реранкер, формат ответа и
шкала уверенности общие; пороги решения — свои у каждого режима
(`QDRANT_OK_FLOOR`/`QDRANT_REVIEW_FLOOR`; для каталога — `CATALOG_*_FLOOR`), контракт v1.0 (`docs/api-contract.md`).

## Строки закупки и три статуса ответа

**Строка закупки — не название товара.** Экспорт из ERP/1С приходит в виде
`Машина стиральная LG F2J3NS0W; бытовая; загрузка 6 кг; отжим 1000 об/мин`. Хвост после
первого `;` (или `|`) — спецификация: бренд, объём, количество. Он не помогает найти позицию,
но сбивает признаки покрытия, поэтому строка скорится **дважды** — целиком и только именем;
побеждает более уверенный ответ, а в `query` всегда возвращается исходный текст
(`ml/query.py`, эксп. 30). Обрезка хвоста не применяется: у 125 названий позиций перечня
сам `;` внутри, и «Плита Kronospan MDF; древесно-волокнистая» без хвоста уезжает в другую
позицию.

**Статусы читаются по-разному, и это не косметика** (UI: `frontend/src/status.ts`):

| Статус | Подпись в UI | Что значит |
| --- | --- | --- |
| `ok` | «Уверенный результат» | код найден с уверенностью выше порога |
| `review` | «Нашёл, но не уверен» | позиция найдена, но рядом похожие названия; на реальных выгрузках код здесь чаще всего верный |
| `not_found` | «Нет в перечне» | надёжного совпадения нет; перечень закрытый, и молчание — корректный ответ для товара вне его состава |

Под молчанием UI различает «похожих позиций нет» и «похожие есть, но уверенности не хватило»
(второе — приглашение посмотреть альтернативы). Если позиция повторяется в перечне под другим
кодом (приложения 2 и 3 — 81 такое семейство), интерфейс говорит об этом прямо, вместо того
чтобы выдавать один код за истину.

**Что это дало на двух реальных выгрузках по 100 строк** (эксп. 30, воспроизведено 100/100
статусов и кодов до правок): `ok` 63 → **108**, `review` 55 → **29**, молчание 82 → **63**,
из которых около 30 — верные (товара нет в перечне: картридж, ручка, аптечка; ИБП тогда
считался таким же, но в эксп. 36 нашлась позиция). Остаток
(~20 строк, где позиция в перечне есть) закрывает третья ступень — `LLM_VERIFIER_*`
(эксп. 32): она подтверждает одну из трёх предложенных позиций и никогда не придумывает код.

## Ограничение частоты запросов

Ответы 429 отдают `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`.
`/health*`, `/metrics` и статика `/ui` не лимитируются. Свои бакеты у
`/admin/*` (строгий лимит на изменяющие операции) и у `POST /classify/file`:
один файл — это до 100 позиций, поэтому загрузки считаются **по файлам**
(`RATE_LIMIT_FILE_RPS=1`, `RATE_LIMIT_FILE_BURST=3`) и не тратят общий лимит
запросов. Счётчик отказов — в `GET /metrics` (`dora_http_rate_limited_total{path}`).

**Кто считается клиентом.** По умолчанию — адрес сокета, а `X-Forwarded-For`
**игнорируется**: иначе любой клиент подставлял бы случайный адрес в заголовок
и получал свежий бакет на каждый запрос. Заголовок читается только если запрос
пришёл от прокси из `TRUSTED_PROXIES` (IP или CIDR через запятую), и берётся
**правый непроверенный хоп** — тот, который дописал ваш прокси; всё, что клиент
дописал слева, не учитывается. Прокси за прокси обходятся справа налево, пока
не встретится адрес не из списка.

```bash
# Укажите фактический IP/узкую CIDR-сеть прокси (пример: 10.0.0.1).
# 21-й запрос с одного адреса → 429.
TRUSTED_PROXIES=10.0.0.1 docker compose up -d
for i in $(seq 1 25); do
  curl -s -o /dev/null -w "%{http_code} " -X POST localhost:8000/classify \
    -H 'Content-Type: application/json' -H "X-Forwarded-For: 203.0.113.7" \
    -d '{"name": "Ноутбук Lenovo"}'
done; echo

# Без прокси (сервис доступен напрямую) адрес берётся из сокета, а подделанный
# заголовок ничего не меняет — те же 429 на том же клиенте.
```

`TRUSTED_PROXIES` обязателен при работе за прокси: без него все клиенты
попадут в один бакет (лимит станет общим на весь сервис). У `uvicorn` в образе
и в примерах запуска стоит `--no-proxy-headers`, чтобы он не переписывал адрес
клиента сам: решение о доверии заголовку принимает только приложение.
Опечатка в `TRUSTED_PROXIES` роняет старт, а не игнорируется молча.

Для нагрузочных прогонов (`scripts/load_test.py`, `eval/api-load-test.md`)
лимит отключают: `RATE_LIMIT_ENABLED=false`. Скрипт сам подсказывает это,
если получил 429.

## ML-модель и переиндексация

```bash
# Готовые артефакты (лексический реранкер + tfidf-эмбеддер) лежат в ml/artifacts/ и входят в
# образ. Пересборка (без интернета, ~2–3 мин на 1 CPU), затем скопировать в ml/artifacts/:
python scripts/build_model.py
cp models/reranker.json models/tfidf_embedder.json ml/artifacts/

# реранкер с векторными признаками под активный эмбеддер (+ проверка предохранителем).
# Гейт переобучает лексическую базу тем же кодом (≈ +3 мин) — иначе сравнение идёт
# с отгруженным артефактом, который не воспроизводится текущим тренером.
# --gate-seeds: вердикт по пулу прогонов (≈ +9 мин на сид). Без флага — один прогон;
# на одном разбиении решение по тишине нестабильно (см. раздел «Предохранитель»).
# Результат проверки: <models-dir>/dense-gate.json (по строкам, с sha256 обоих артефактов).
python scripts/build_model.py --dense --gate --gate-seeds 1875,1876,1877,1878 --models-dir models
cp models/reranker.tfidf.json models/dense-gate.json ml/artifacts/   # если эмбеддер tfidf
```

Лемматизация (`pymorphy3`) встроена в `ml/features.stem` — основы в артефакте построены по
леммам, поэтому `pymorphy3` обязателен в рантайме (он в `api/requirements.txt`). После смены
каталога/стеммера артефакт нужно пересобрать.

### Где лежит модель и откуда её «скачивать»

Модель — это **файлы в репозитории**, а не пакет из интернета: `ml/artifacts/reranker.json`
(лексический реранкер, ~80 КБ), `ml/artifacts/tfidf_embedder.json` (эмбеддер для
`VECTOR_SEARCH=true`) и `ml/artifacts/reranker.tfidf.json` (реранкер с векторными признаками).
Они входят в git и в Docker-образ (`api/Dockerfile`), поэтому «скачивать» ничего не нужно —
достаточно того же коммита:

```bash
git clone <репозиторий> && cd Dora-B2BCase     # модель уже здесь
git cat-file -s HEAD:ml/artifacts/reranker.json # ~84 КБ, sha256 — в ml/artifacts/README.md
docker compose up --build api                   # то же внутри образа, офлайн
```

Тяжёлый эмбеддер (`ru_core_news_md` / bge-m3) — единственное, что скачивается, и только при
сборке образа (`MODEL_NAME`, `MODEL_LOCAL_ONLY=true`). Внешняя модель нужна лишь семантическому
режиму; каталоговый работает на файлах из репозитория и без интернета. Если артефакт нужно
положить отдельно (например, в том `MODELS_DIR`), это копирование файла, а не установка:

```bash
docker compose cp api:/app/ml/artifacts/reranker.json ./reranker.json   # забрать из контейнера
MODELS_DIR=/mnt/models docker compose up api                           # или подложить свой
```

Проверить, что отгруженный файл — это то, что даёт текущий код (а не «какой-то» артефакт):
`python scripts/check_artifacts.py models/reranker.json ml/artifacts/reranker.json` — CI делает
это на каждом PR шагом «Shipped artifacts match a rebuild».

Каталог обновляется **без передеплоя**: `POST /admin/catalog` кладёт новый `data.csv` на общий
том, а API и воркер сами пересобирают классификатор и векторный индекс при следующем запросе
(проверяется сигнатура файла). `POST /admin/reindex` нужен только режиму `qdrant`.

Ошибочная загрузка **откатывается одной командой**: каждая загрузка сохраняет снимок
заменяемого каталога, `POST /admin/catalog/rollback` возвращает предыдущую редакцию и сразу
сбрасывает кэши (перезапуск не нужен), `GET /admin/catalog/export` отдаёт текущий файл для
внешней копии. Хранится 10 последних снимков (`CATALOG_SNAPSHOT_KEEP`).

## Мониторинг

`GET /metrics` отдаёт метрики в **текстовом формате Prometheus**
(`text/plain; version=0.0.4`) — скрейпится без экспортёров; клиенты с
`Accept: application/json` получают легаси-снимок для отладки. Ключевые
семейства: `dora_http_requests_total{path,method,status}`,
`dora_http_request_duration_seconds{path}` (гистограмма),
`dora_http_rate_limited_total{path}`,
`dora_classifications_total{mode,backend,status}`,
`dora_batch_jobs_total{event}` и гейджи здоровья —
`dora_classifier_up`, `dora_embedder_up`, `dora_vector_store_up`,
`dora_vector_positions`, `dora_build_info{version,…}`.

`GET /health/ready` дополнительно несёт блок `vector_health` — живой статус
эмбеддера и векторного хранилища (TTL-кэш: пинг Qdrant не чаще раза на
интервал) — и поле `llm_verifier`: `off` либо `on:<модель>` (третья ступень,
эксп. 32). Деградация хранилища не снимает readiness (поиск уходит в память),
но видна в `vector_health.degraded=true` и в гейдже `dora_vector_store_up=0`.

Ограничение: при `QUEUE_BACKEND=celery` инференс идёт в процессе воркера, у
которого нет HTTP-эндпоинта, — счётчики классификаций воркера в `/metrics` API
не попадают (прогресс задач — через `GET /classify/batch/{job_id}`). Подробный
контракт метрик — `docs/api-contract.md`, раздел «Наблюдаемость».

## Обновление каталога перечня

Регламент — `docs/catalog-update.md`. Коротко: `POST /admin/catalog`
(`dry_run=true` — проверка без установки) принимает CSV/JSON, валидирует
строки и атомарно заменяет `data.csv` + `data.json`; затем
`POST /admin/reindex` (или `auto_reindex=true`). Для проверки файла без API:
`python scripts/validate_catalog.py new_catalog.csv`. Перед загрузкой полезно
сделать `GET /admin/catalog/export`, после неудачной — `POST /admin/catalog/rollback`.

## Качество и оценка

- Размеченный набор: `eval/labeled_examples.csv` (274 запроса; колонка `label_kind`:
  201 `code`, 32 `absent`, 41 `unclear`). `unclear` — строки, где покрыть товар может
  только остаточная позиция («прочие / не включённые в другие группировки»): они не
  входят в проценты, пока по ним не выскажется юрист. Правила и построчный разбор —
  `docs/labeling-doctrine.md` и `eval/label_audit.csv`; инварианты набора проверяет
  `api/tests/test_labeled_set.py`.
- Прогон: `PYTHONPATH=api python eval/run_eval.py [--sweep]` → `eval/eval_report.md`
  (top-1/top-3, доля верного `not_found`, регрессия на точных названиях
  каталога, обе шкалы уверенности `confidence_raw`/`confidence` и ECE, свип
  порога `review`, разбор ошибок).
- Перекрёстная проверка порога `review`: `PYTHONPATH=api python eval/threshold_cv.py`
  — прежде чем брать «лучшую» клетку из свипа, показывает, переносится ли она на
  отложенные строки (на 274 строках ответ: нет, прирост меньше строки на фолд).
- Контур разметки: `PYTHONPATH=api python eval/feedback_loop.py --input <выгрузка>.csv`
  превращает вердикты специалиста (`user_verdict`/`corrected_code`) в файл меток
  `eval/labeled_from_feedback.csv` и печатает, сколько строк полосы `review` оказались
  верными и сколько отвеченных строк — «нет в перечне». Набор измерения при этом не
  изменяется; выгрузка без вердиктов не импортирует ничего (эксп. 33).
- Разбор ошибок по механике: `PYTHONPATH=api python eval/review_errors.py`
  делит неверные ответы на «соседний код», «мост + обобщающая позиция» и прочие и
  показывает, какие из них размечены противоположным образом — то есть являются
  вопросом к разметке, а не к модели (разбор: `eval/experiments.md`, эксперимент 23).
  С `--brief docs/label-questions.md` собирается готовый документ для специалиста по
  нацрежиму: по каждой спорной строке цитируются обе позиции каталога и рядом стоит
  строка с той же механикой и противоположным вердиктом.
- Синтетический бенчмарк без разметки: `PYTHONPATH=api python eval/synthetic_eval.py`
- **Стресс-набор по спецификаторам** (`eval/specifier_stress.py`, эксп. 35): из каталога
  детерминированно строятся строки в форме реальной закупки — точное название позиции, первые
  3-4 слова названия и продуктовое слово моста, каждое само по себе и с 1-3 техническими
  атрибутами («220 В», «IP54», «16 ГБ», «цифровой», «трёхфазный»). Отвечает числами на вопрос
  «сколько стоит спецификация»: точное название 97.3 % → с атрибутами 96.0 %, короткая строка
  83.2 % → 78.2 %. Записанный замер — `eval/baselines/specifier_stress.json`, падение больше
  0.5 п.п. роняет `api/tests/test_specifier_stress.py`, поэтому изменение, полезное на 201
  размеченной строке и вредное на реальных, больше не проходит незамеченным.
- Абляция расхождений обучения и API (шортлист, fallback): `PYTHONPATH=api python eval/serving_ablation.py`
  → `eval/synthetic_report.md` (информационный, CI-гейт его не проверяет).
- Сравнение артефактов **при равной тишине**, а не при равном пороге:
  `PYTHONPATH=api python eval/pareto.py --detail [--extra имя=путь[:dense]]` — для каждого
  артефакта берёт его собственные уверенности как сетку порогов и печатает «при тишине не ниже
  N — самый разговорчивый порог, который её держит». Так отвечается вопрос «какой артефакт
  лучше», который нельзя решить сравнением заголовочных процентов (эксп. 18).
- Сравнение режимов `catalog` и `qdrant` на одном наборе:
  `PYTHONPATH=api python eval/backend_comparison.py --markdown eval/backend_comparison.md`
  → `eval/backend_comparison.csv` + отчёт; семантический прогон со свипом —
  `eval/run_eval.py --backend qdrant --output eval/eval_report_qdrant.md`.
  Итог эксп. 15 (на тогдашних артефактах): лексика 83.7% top-1 против 79.5% у семантики при ×4 латентности,
  поэтому режим по умолчанию — `catalog` (`eval/experiments.md`); на артефактах эксп. 29
  разрыв шире — 95.0% против 68.7% (`eval/backend_comparison.md`).
- Пороги под семантическую шкалу (эксп. 16, перемерено в 28): `PYTHONPATH=api python
  eval/threshold_sweep.py --backend qdrant --output eval/threshold_sweep_qdrant.csv` —
  снимает сырые уверенности за один проход и считает сетку порогов мгновенно.
  `review = 0.45` — плато 0.42–0.45, на котором одновременно лучше обе стороны: 153 верных
  решения против 147 при 0.25 и 4 ложных кода вне перечня против 14 (эксп. 28; перемерено
  в 29 на новых артефактах — 68.7% top-1 и 90.6% тишины, CV: «подбирать нечего»).
  Применяется через `QDRANT_REVIEW_FLOOR`/`QDRANT_OK_FLOOR`; порог ниже измеренного поднимает
  предупреждение в логе.
- CI-гейт качества: job `quality` в `.github/workflows/lint.yml` пересобирает модель,
  проверяет, что отгруженный `ml/artifacts/reranker.json` **байт в байт** совпадает со свежей
  сборкой, и сравнивает метрики размеченного набора с записанным замером
  (`eval/baselines/lexical.json` и `eval/baselines/dense-tfidf.json`) — по строкам, а не по
  процентам: любая метрика может потерять одну строку из 201/233, `ok_precision` сравнивается
  по числу неверных уверенных ответов, ECE не может вырасти больше чем на 0.01. Правило —
  `eval/quality_gate.py`; обновление базовой линии — осознанный коммит с объяснением
  (почему пороги-проценты больше не используются — `eval/experiments.md`, эксп. 20).
- Эксперименты и выводы: `eval/experiments.md`.
- Нагрузочный замер: `eval/api-load-test.md`, `scripts/load_test.py`.
- План следующих работ (мерж, часть D на целевой машине, известное
  train/serve-расхождение): `docs/next-steps.md`.

## Структура

```
api/
  app/
    main.py            # FastAPI: роуты, admin-каталог, lifespan, статика /ui
    schemas.py         # контракт v1.0 (Pydantic)
    job_store.py       # хранилища задач: memory / sqlite
    job_store_postgres.py  # PostgreSQL: задачи, прогресс, журнал классификаций
    dispatch.py        # отправка пакета: фоновая задача FastAPI или Celery
    tasks.py           # тело пакетной задачи (общее для API и воркера)
    worker.py          # Celery-приложение (брокер Redis)
    core/              # config, logging, correlation id, metrics
    middleware/        # observe, ограничение размера тела, rate limit
    services/          # classifier (catalog/mock/qdrant), catalog_io, source_lookup
  tests/               # API, классификатор, контракт, очередь, PostgreSQL, векторы, compose
frontend/              # демо-UI (React + Vite; собирается в frontend/dist и отдаётся на /ui/)
ml/                    # эмбеддеры, плотный индекс + Qdrant (dense.py), реранкер, лексика, обучение
  artifacts/           # готовые артефакты модели (входят в образ)
data/                  # каталог ПП № 1875 (data.csv + data.json + source_text.txt)
eval/                  # размеченный набор, метрики, эксперименты, чек-листы
docs/                  # api-contract.md, catalog-update.md
scripts/               # build_model, download_model, parse_pp1875, validate_catalog, load_test, docker_smoke
```

> Задачи пакетной обработки лежат в PostgreSQL (в Docker), поэтому переживают перезапуск и
> API, и воркера. Задачи, которые никто не трогал дольше `JOB_STALE_SECONDS` (воркер умер),
> помечаются `failed`, а не висят вечно; недоступная очередь даёт `503`.
