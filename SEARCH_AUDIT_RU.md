# Проверка поиска и точности Dora-B2BCase

Проверено 23.10.2026: ветка main, commit c18f2c4f626586478889f2d7f7f1dd976e7333e5.
Проверка ограничена классификацией, поиском и оценкой качества. Изменений на GitHub нет.
Ссылка на постановление, source_lookup, каталог и фронтенд в этом пакете не изменены.

## Что означает требование 85%

В приложенной презентации, слайд 14: «Точность классификации ≥ 85% на тестовом датасете (20 товаров)».
Это минимум 17 правильных основных ответов из 20. Уверенность отдельного ответа, средняя уверенность
и доля статусов ok не заменяют эту метрику. Правильный код со статусом review остаётся правильной
классификацией, если приёмка отдельно не запрещает ручную проверку. Условие не уточняет глубину кода
и обработку неоднозначных товаров: это необходимо зафиксировать в разметке до запуска теста.

В репозитории найден набор из 274 строк: 166 с кодом и 108 с ожидаемым not_found, 17 помечены disputed.
Он уже многократно использовался для выбора моделей и порогов. Приёмочные 20 товаров в этой работе
не подбирались по успешным ответам. Для подтверждения готовности нужен независимый заранее
размеченный набор, который не использовали при настройке.

## Воспроизведённые результаты

Среда: Python 3.12, Linux, текущий ml/artifacts/reranker.json, pymorphy3 2.0.6.
Запуск: VECTOR_SEARCH=false, backend=catalog, без переобучения, без изменения меток.
Это воспроизводимый лексический baseline, а не измерение вашего запущенного Docker/E5.

|---|---:|
| Top-1 с кодом, правила исходного run_eval.py | 145/166 = 87,35% |
| Top-1 по всем строкам, правила исходного run_eval.py | 223/274 = 81,39% |
| Строгое совпадение кода, товары с кодом | 142/166 = 85,54% |

Исходный скрипт выводит проценты с одним десятичным знаком. При строгом сравнении дополнительно
теряются две строки телевизоров и одна строка дорожного катка: ожидаемый родительский код отличается
от выданного дочернего. Это различие правил оценки; оно само по себе не доказывает ошибку классификации.
В частности, ожидаемый 26.40.20 у двух телевизоров буквально отсутствует в каталоге, где есть его
детализированные коды. Такие строки сначала требуют согласования допустимых ответов.

В сохранённом eval/eval_report_qdrant.md: 74,1% по товарам с кодом, 83,2% по всему набору и 97,2%
правильных not_found. Это исторический отчёт из репозитория, не новый прогон. Также backend_comparison.md
содержит другой результат catalog, чем eval_report.md. Без версии модели, каталога и настроек эти
отчёты нельзя считать замером одной и той же работающей сборки.

## Подтверждённые проблемы

### 1. E5 теряет префиксы после копирования в Docker

Файлы: ml/embedder.py, scripts/download_model.py, api/Dockerfile, docker-compose.yml.
_e5_prefixes определяет тип модели по наличию e5 в MODEL_NAME. Но Docker сохраняет выбранную
intfloat/multilingual-e5-small в /opt/models/embedder. В этом имени e5 нет, поэтому оба префикса пусты.
Для E5 авторы требуют query: для запроса и passage: для документа, в том числе для русского текста.
Источник: https://huggingface.co/intfloat/multilingual-e5-small

Включённое исправление: загрузчик сохраняет исходный model_id в dora_model.json. Encoder читает
идентичность модели из этого файла, а не из имени папки. Новый tag включает версию формата входа,
поэтому старые кэши и reranker не принимаются за совместимые с исправленными векторами.
Для старой папки embedder без метаданных необходим повторный запуск обновлённого загрузчика или
пересборка образа. Простая замена Python-файла не добавляет метаданные в существующие веса.

### 2. В режиме qdrant запрос кодируется как документ

Файл: ml/search.py. search_many вызывает encode_texts, который у SentenceTransformerEncoder
использует document prefix. При корректно распознанной E5 это passage: вместо query:.
Включённое исправление: поиск вызывает encode_queries. Индексация документов продолжает использовать
документное кодирование. Для симметричных fallback-энкодеров интерфейс сохраняет прежнее поведение.

### 3. Top-3 фактически включает четыре варианта

Файлы: eval/run_eval.py и api/app/services/classifier.py.
API возвращает основной код плюс до трёх альтернатив. _classify_rows засчитывает любую из них.
Воспроизведено на «Эндопротез тазобедренного сустава» и «Стол кухонный»: правильный код четвёртый,
но исходный отчёт считает Top-3 успешным. Для приёмки нужен Top-1. Новый acceptance_eval.py отдельно
считает Top-1 и первые три различных кода, включая основной ответ.

### 4. Текущий gate проверяет другой режим и другой знаменатель

В .github/workflows/lint.yml выставлено VECTOR_SEARCH=false. --min-top1 85 в run_eval.py проверяет
только 166 строк с кодом, хотя по всему набору метрика ниже. Фактически векторный слой при этом не
проверяется. CI дополнительно обучает свой артефакт, поэтому его результат может отличаться от
поставляемого ml/artifacts/reranker.json. Прохождение такого gate не доказывает 85% на приёмке
и не гарантирует работу E5 внутри запущенного контейнера.

### 5. Измерительный набор используется для выбора модели

scripts/build_model.py: gate_dense читает eval/labeled_examples.csv и оставляет либо удаляет
векторный reranker по результатам на нём. api/Dockerfile запускает --dense --gate.
Это выбор модели на eval-наборе, хотя комментарии называют его чисто измерительным. Весов на этих
строках напрямую не обучают, но независимым финальным тестом этот набор уже не является.
Нужны отдельные train, development/validation и закрытый test. Модель, пороги и словарь синонимов
подбираются по development; итоговый test используется только для подтверждения.

### 6. Разбиение обучения идёт по парам, а не по запросам

ml/train_reranker.py: rng.shuffle(pairs), затем срез train/validation. Разные кандидаты одного
запроса могут оказаться в обеих частях. Затем confidence_model обучается и проверяется на одних
group_rows; пороги также выбираются на этих строках. Это делает внутреннюю оценку уверенности
слишком оптимистичной и не моделирует реальный полный список конкурирующих кандидатов.
Исправление следующего этапа: разделять целые группы запросов, а лучше семейства товаров/вариантов
наименований; отдельно выделить данные для калибровки и выбора порогов. После этого переобучить модель.

### 7. Одинаковые названия теряют коды при обучении

В data/data.csv: 1126 строк, 746 уникальных названий, 984 пары название–код; у 87 названий более
одного кода. build_pairs и build_calibration_cases строят code_by_title как обычный словарь,
оставляя последний код для одинакового названия. Метка пары задаётся совпадением названия.
Например, единое название про медицинские морозильники и холодильники связано с 28.25.13.110,
28.25.13.116 и 32.50.50. Различия между этими кодами таким обучающим представлением не описаны.

Следующее исправление: хранить кандидата по record_id или паре название–код; добавить проверенные
описания конкретных подкодов и характеристик. Текст для поиска должен различать назначения и типы
товаров. Одного номера кода рядом с одинаковым названием недостаточно, чтобы научить модель смыслу
различий. Исходные ссылки и record_id можно сохранить.

### 8. Списки кандидатов при обучении и в работе различаются

CatalogClassifier отбирает 25 лексических строк и до 8 векторных. Обучение использует 12 лексических
кандидатов, уникальные названия и принудительно добавляет правильное название, если поиск его потерял.
Чистый qdrant берёт 10 строк, среди которых могут быть повторы из приложений. Дедупликация альтернатив
происходит уже после поиска. Поэтому заявленное одинаковое распределение кандидатов не выполняется.

Для улучшения сначала измерять Recall@K ДО ранжирования: попадает ли допустимый код в список.
Если его нет, менять поиск/описания/размер списка; если есть, но выбран другой, менять ранжирование;
если победитель правильный, но ответ отсекает порог, калибровать порог. Объединённый поиск в catalog
уже существует: переписывать его с нуля или просто переключаться на qdrant не требуется.

### 9. Разметка и фильтры каталога требуют отдельной проверки

У «Монитор 24 дюйма» недостаточно признаков назначения для выбора между двумя позициями;
строка помечена disputed. Для «Компьютер настольный» комментарий предполагает отсутствие 26.20.14,
хотя код есть в текущем каталоге. В некоторых отрицательных строках основание записано как
«нет в data.csv, проверено grep»; отсутствие конкретного бытового слова не проверяет охват общей
категорией. Нельзя исправлять такие метки только потому, что модель выдала другой ответ.

Кроме того, каталог содержит строку code_role=Исключение и шесть строк без кода из приложения 4.
Оба загрузчика допускают их к поиску; флаги сейчас в основном информационные. Правила включения
нужно задавать с учётом приложения и смысла позиции, не делать безусловное удаление по одному флагу.
В этой работе юридическая разметка и состав каталога не менялись.

## Что делать по порядку

1. Снять /health/ready и прогнать acceptance_eval.py через HTTP по работающему API. Сохранить исходный
   результат, каталог, веса и переменные запуска. Проверить embedder и scoring; fallback на tfidf/spacy
   или lexical-reranker означает, что эксперимент с transformer/dense reranker фактически не состоялся.
2. Проверить неоднозначные эталоны и согласовать уровень кода. Допустимые точные альтернативы задать
   заранее через accepted_okpd2. Не считать любой родительский код автоматически правильным.
3. Применить исправления входов E5, пересоздать векторы и артефакт ранжирования для нового tag.
   Сравнить на development. Сначала оставить существующий гибридный catalog.
4. Исправить train/validation split и потерю кодов в code_by_title; унифицировать формирование
   кандидатов обучения и API. Переобучить, затем калибровать порог на отдельной части development.
5. На development проверить размеры списка, например 25/50 кандидатов, Recall@K и Top-1. Это
   варианты эксперимента, а не обещанный прирост. Синонимы и товарные примеры добавлять в поисковое
   описание, сохраняя материал, назначение и признаки, влияющие на код. Бренды/модели обрабатывать
   осторожно: удаление всех цифр или характеристик может ухудшить различение товаров.
6. Только после фиксации конфигурации проверить независимые 20 товаров и дополнительный набор
   из 100 реалистичных позиций. Отдельно измерить одиночную и массовую обработку с реальными весами.

## Что проверено в пакете и что остаётся неизвестным

73 целевых теста прошли: новые тесты префиксов/кодирования/метрик плюс существующие тесты поиска,
reranker, Qdrant-кандидатов, лексикона и калибровки. Ruff проверил шесть файлов пакета.
Старый лексический baseline воспроизведён; новый строгий evaluator вернул FAIL 220/274, как и должен.
Тесты используют детерминированный encoder и подмену модели; веса E5/BGE здесь не загружались.
Проверки не подтверждают улучшение реальной точности до 85% и не измеряют ваш работающий сервер.
HTTP-режим подготовлен для такого замера; к вашему серверу в этой сессии доступа не было.
Сборка всего проекта и остальные подсистемы не входят в этот аудит.

## Состав изменений

- ml/embedder.py: сохранение идентичности модели и префиксов при локальном пути, новая версия tag.
- ml/search.py: query encoder для поисковых запросов.
- scripts/download_model.py: запись model_id рядом с весами.
- eval/acceptance_eval.py: независимая оценка произвольного CSV, строгий Top-1 по всем строкам,
  отдельные метрики для положительных/отрицательных примеров, настоящий Top-3, SHA256 датасета,
  сведения о загруженном поиске, ошибки запросов в знаменателе. Порог не сравнивается с округлённым числом.
- Два файла регрессионных тестов.

Исходный run_eval.py, workflow CI, обучение и пороги пока не менялись. Их проблемы перечислены выше.
Пакет — первый проверенный этап исправлений, не подтверждение полной готовности проекта.
