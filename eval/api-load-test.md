# API load smoke test

**Дата:** 2026-10-07 (UTC)  
**Режим:** локальный FastAPI `catalog`, Python 3.11.2, Linux sandbox; запуск не через Docker.  
**Каталог:** 1 126 записей из `data/data.csv`; ML-модель и Qdrant в этом прогоне не использовались.

## Команда

> **Rate limit:** нагрузочный скрипт дергает API чаще, чем лимит по умолчанию,
> поэтому целевой API запускается с `RATE_LIMIT_ENABLED=false` (иначе скрипт
> остановится с понятным сообщением на первом же 429).

```bash
RATE_LIMIT_ENABLED=false PYTHONPATH=api python scripts/load_test.py \
  --base-url http://127.0.0.1:8000 \
  --concurrency 10 \
  --items 100 \
  --pid <PID_UVICORN>
```

## 2026-10-21 — BE-7: прогон 10×100 до/после + обоснование `MAX_CONCURRENT_INFERENCES=1`

**Дата:** 2026-10-21 (UTC). Раздел заменяет протокол 2026-10-07 выше по целям BE-7;
старые цифры оставлены как история (другое окружение: без векторного поиска, другой скрипт).

**Среда:** Linux sandbox, 2 vCPU / 4 ГБ, Python 3.11, один процесс uvicorn,
`JOB_STORE=memory`, `VECTOR_SEARCH=true` (Qdrant local-mode + tfidf dense — веса
трансформера в sandbox недоступны), `LOG_LEVEL=WARNING`, rate limit выключен.
«До» — код базового коммита `4ef6941` (git worktree), «после» — ветка BE-6/7/9;
обе стороны запускаются одним интерпретатором и одним venv.

### Протокол

10 batch-задач × 100 товаров, 10 одновременных клиентов. Каждый прогон **холодный**:
скрипт получил флаг `--tag <уникальный префикс>` — имена товаров уникальны между
прогонами, поэтому response-кэш, кэш запросов dense-индекса и кэш rate limit не
переносятся. 3 прогона на вариант, в таблице медианы. Команда:

```bash
LOG_LEVEL=WARNING RATE_LIMIT_ENABLED=false VECTOR_SEARCH=true \
MAX_CONCURRENT_INFERENCES=<N> JOB_STORE=memory PYTHONPATH=api \
  python -m uvicorn app.main:app --host 0.0.0.0 --port <PORT> --log-level warning

python scripts/load_test.py --base-url http://127.0.0.1:<PORT> \
  --concurrency 10 --items 100 --pid <PID_UVICORN> --tag <run-id>
```

Скрипт теперь печатает p50/p95/p99 отдельно для приёма задач, опроса статуса и
записи SSE, плюс пиковый RSS сервера (`--pid`); итог дублируется JSON-структурой.

### Результаты (медианы трёх холодных прогонов 10×100)

| Вариант | Стена, с | Приём p95, мс | Опрос p50 / p95, мс | Пик RSS, МБ |
| --- | ---: | ---: | ---: | ---: |
| До (`4ef6941`), MCI=1 | 46.76 | 49.18 | 29.89 / 51.00 | 139.7 |
| После, MCI=1 | 46.38 | 50.29 | 29.73 / 52.62 | 146.7 |
| После, MCI=2 | 46.71 | 79.95 | 48.39 / 98.00 | 158.1 |
| После, MCI=4 | 46.81 | 73.93 | 108.18 / 208.65 | 194.8 |

Разброс стен между прогонами одного варианта ±5 % (у «до»: 50.08 / 46.76 / 46.27 с).

### Выводы

1. **Без деградации p95 (DoD BE-7):** после изменений приём p95 50.29 мс против
   49.18 мс, опрос p95 52.62 против 51.00 — разница в пределах шума прогонов;
   стена даже чуть ниже (46.38 против 46.76 с). Все 1000 позиций обработаны,
   0 неуспешных задач во всех вариантах.
2. **`MAX_CONCURRENT_INFERENCES=1` обоснован:** на 2 vCPU с GIL-bound инференсом
   MCI=2 и MCI=4 **не дают прироста пропускной способности** (стена та же,
   ~46.7–46.8 с — задачи всё равно упираются в CPU), но ухудшают отклик API:
   опрос p95 растёт в 1.9× (MCI=2) и 4.1× (MCI=4), приём p95 в 1.5×, пик RSS
   +12 / +48 МБ (больше задач одновременно держат payload и результаты в памяти).
   Семантика: семафор ограничивает инференс **внутри одного процесса**;
   горизонтальное масштабирование — процессами (`--workers` / реплики API) или
   Celery-воркерами (`worker --concurrency=N`), у каждого свой лимит.
3. **Батчевый энкодинг запросов** (`DenseIndex.warm_queries` +
   `classify_many`): микро-бенчмарк на 100 запросах (55 уникальных) — старый
   путь делал 55 вызовов энкодера (по одному на уникальный запрос), новый делает
   **1 вызов на 55 текстов**; решения классификатора побитово совпадают. В реальной
   batch-задаче `run_batch_job` греет запросы чанками `BATCH_CHUNK_SIZE=16`:
   ≤7 вызовов энкодера на задачу из 100 позиций вместо ≤100. При
   смоделированном накладном расходе 5 мс на вызов энкодера (порядок
   инициализации токенайзера/торч-контекста у ST-моделей) батчинг экономит
   ~0.2 c на каждые 100 запросов; у tfidf-энкодера накладные расходы на вызов
   пренебрежимы, поэтому в sandbox выигрыш виден прежде всего в числе вызовов. Полноценный замер на целевой машине (e5-small, `MODEL_BATCH_SIZE=16`) —
   по чек-листу `eval/docker-target-checklist.md`, шаг 13.
4. **Единый прогрев классификатора** (`get_classifier()` под семафором MCI):
   холодный старт больше не конкурирует сам с собой — первый же запрос прогревает
   каталог/эмбеддер/Qdrant один раз, последующие проходят через
   `asyncio.wait_for(..., timeout=CLASSIFIER_WARMUP_TIMEOUT_S)` без повторной
   загрузки. В прогонах выше эффект входит в итоговые числа (сервер стартовал
   холодным).
