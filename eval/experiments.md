### 2. Запас CI-гейта по тишине

Гейт `--min-silence 91` при 48 строках «вне перечня» (1 строка = 2.08 п.п.): текущие 44/48 = 91.7%, один
промах даёт 43/48 = 89.6% → красный билд. Гейт 89 пропустит один промах (43/48) и упадёт на двух (42/48 = 87.5%).
Остальные гейты: top-1 139/166 при гейте 83 (порог — 138 верных, запас одна строка), top-3 148/166 при гейте 88
(порог — 147, запас одна строка), точные названия 112/112 при гейте 98 (порог — 110, запас две строки).

Варианты: (а) снизить гейт тишины до 89 — честно отражает разрешение набора (но ослабляет гейт);
(б) расширить набор «вне перечня» до 100+ строк, проверенных grep'ом по `data/data.csv`, и держать гейт 91 —

## Калибровка шкалы `confidence` (эксп. 10, часть C)

**Проблема.** Сырая уверенность модели уверенности откалибрована на *синтетических*
группах: там её ECE 0.019, но группы заметно труднее реальных запросов. На
размеченном наборе при сырой уверенности 0.3–0.7 точность 0.84–1.0, то есть
шкала систематически занижена — ECE 0.37, число нельзя читать как вероятность.

**Решение.** Контракт не меняется по смыслу, но расширяется: `confidence_raw` —
сырая уверенность, **по ней принимается `status`**; `confidence` — она же после
монотонной калибровки Платта (`sigmoid(a·logit p + b)`), её видит пользователь.
Монотонность гарантирует, что статусы не зависят от калибровки (проверяют
`api/tests/test_calibration.py::test_confidence_model_decides_on_raw_ignoring_calibration`
и `...::test_statuses_follow_the_raw_confidence_on_the_labeled_set` — на всех 214
строках статус равен `status_for(confidence_raw)`, до/после совпадает).

**Калибровочная площадка** (`ml/train_reranker.build_calibration_cases`), из
источников, не совпадающих с `eval/labeled_examples.csv`:

| Источник | Запросов | Отвечено | Смысл |
| --- | ---: | ---: | --- |
| `ml.lexicon.BRIDGES` + нейтральные модификаторы (демисезонные/спортивные/зимние/…) | 330 | 283 | курируемые человеком пары «бытовой запрос → каноническая позиция» |
| OOV-пробы `make_negative_queries` (промахи вне перечня) | 370 | 80 | любой ответ — ошибка, верное поведение — тишина |
| **Итого** | **700** | **363** | ECE площадки 0.309 → 0.117 |

Запросы площадки прогоняются через точную копию каталожного пайплайна API
(shortlist 25 → реранкер → модель уверенности, лексические скоры как в проде
с эксп. 12); расхождение с живым классификатором ловит тест-дрейф
`test_calibration_platform_mirrors_the_api_confidence` (raw совпадает до 5e-5).
Пересечение запросов площадки с labeled-набором пусто
(`test_calibration_platform_does_not_reuse_labeled_queries`).

**Форма карты.** Свободный фит по log-loss уводит наклон к максимуму (площадка
уверенно права уже с 0.32) и прижимает шкалу к 1.0. Поэтому выбирается
*самый мягкий* наклон, который ещё укладывается в цель ECE ≤ 0.12 на площадке
(`PLATFORM_ECE_TARGET`, шаг сетки 0.05): получилось `a = 1.85`, `b = 2.35`
(артефакт v3). Мягкая карта сохраняет разрешение там, где решается судьба
ответа (`review`): 0.25 → 0.58, 0.4 → 0.83, 0.5 → 0.91, 0.75 → 0.99.

**Результат на измерениях** (метрики `eval/run_eval.py`, 5 корзин):

| Набор | Отвечено | ECE сырая | ECE калиброванная |
| --- | ---: | ---: | ---: |
| 89 строк (исходный измеритель) | 78 | 0.372 | **0.055** |
| 214 строк (после C2) | 156 | 0.355 | **0.038** |

Проверка «не подгонка под лексику набора»: если собрать площадку заново, выбросив
все 41 мостовое слово, встречающееся в labeled-запросах (578 кейсов), карта
получается почти той же (`a=4.05/b=4.36` до ограничения наклона) и ECE на
labeled-наборе 0.067 (мягкая карта артефакта даёт 0.038) — перенос не держится на общих словах.

**Цена решения.** ECE на жёстких синтетических валидационных группах растёт
0.019 → 0.125: одна монотонная карта не может быть хороша на двух разных
распределениях, приоритет отдан реальному трафику (и `meta.validation_ece`
теперь честно это показывает).

**Найденный дефект (вне C1, исправлен в эксп. 12).** `CatalogClassifier._rank_to_response` передавал
реранкеру `retrieval_score=0.0` для всех кандидатов, поэтому обученный признак
`retrieval_margin` (вес 1.27 в модели уверенности) в проде всегда 0 — часть
занижения шкалы объясняется этим train/serve-расхождением. Если передавать
реальные лексические скоры, сырая ECE на labeled-наборе падает 0.355 → 0.301 и
статусов `ok` становится 55 вместо 33 (из 214) — то есть меняются статусы, что
запрещено рамками C1. Рекомендация: отдельный PR, после которого калибровку
можно пересобрать (карта станет заметно ближе к единичной). → см. эксп. 12.

**Как воспроизвести:** `python scripts/build_model.py` (сборка ~6 мин, площадка
~20 с) → `PYTHONPATH=api python eval/run_eval.py` (в отчёте появляются обе шкалы,

## Решение по режиму классификации (пункт плана «выбрать режим»)

Для демо по умолчанию остаётся **каталоговый гибрид** (`CLASSIFIER_BACKEND=catalog`:
лексическая выдача + обученный реранкер + откалиброванные пороги) — он работает
без весов и интернета и покрывает большинство запросов из размеченного набора.
**Семантический режим** (`CLASSIFIER_BACKEND=qdrant` + модель в `models/`,
например `bge-m3`) включается тем же контрактом API и проходит те же тесты
(`api/tests/test_ml_e2e.py`); он нужен для абстрактных категорий («костюм» →
«Одежда, кроме одежды из меха»), где лексики недостаточно. Реранкер и пороги
общие для обоих режимов.

## Исправление train/serve-расхождения (эксп. 12)

  скоры, отсортированные по убыванию, и скор топ-кандидата совпадает с лексическим
  скором из `ml.features`. На старом коде оба теста падают;
- модель пересобрана (веса обучения не изменились — обучение и раньше было на

  выдано .110). Обе — соседние позиции той же группы; до изменения они были
  неверными с `review`. Статус `ok` для них — цена исправления;
- 1 неверная строка `review` → `not_found` («Свитер трикотажный мужской»: было
  неверное 14.1, ожидалось 14.3) — на top-1 не влияет;
- 1 строка «вне перечня» `not_found` → `review` («Сушилка для обуви», выдано 15.2) —
  это и есть причина падения тишины на 2.1 п.п.

Итог по `ok`: 53 верных из 55 (раньше 33 из 33). Точность в корзинах калибровки на
отвеченных запросах: 0.8–1.0 → 94.1%, 0.6–0.8 → 72.7%, 0.4–0.6 → 80%.

**Пороги.** `REVIEW_CONFIDENCE_FLOOR` (0.165) и порог `ok` не менялись вручную: свип
на новой модели даёт то же плато (0.16–0.18). Вопрос «не выдавать ли `ok` на соседних
позициях» — это решение по политике тишины, а не калибровка, и оно вынесено в
отдельное обсуждение; при желании ужесточить `ok` — отдельный эксперимент.

**CI-гейт.** Пороги `83 / 88 / 91 / 98` проходят. Запас по тишине сократился до
0.7 п.п. (91.7 при гейте 91): одна строка «вне перечня» — 2.1 п.п., поэтому гейт
на тишину при следующей правке модели может краснеть от одной строки.

**Цена на валидационных группах.** ECE калиброванной шкалы на жёстких синтетических
группах (`meta.validation_ece`) выросла 0.125 → 0.219: карта подогнана под реальный
трафик, а не под эти группы (та же логика, что в эксп. 10).

## Известные ограничения

- **Расхождение shortlist при обучении и в проде (эксп. 12, измерено в эксп. 13).** API добавляет в шортлист
  кандидатов по подстроке (`0.2 * matched / len(tokens)`) и берёт top-25, обучение — top-12 без fallback.
  Абляция на 874 запросах: статусы и коды не меняются, сырая уверенность — до 0.03 в 30 строках. Пересборка
  модели для выравнивания не нужна; решение, выравнивать ли по fallback, не принято.

- Мосты `ml/lexicon.py` закрывают типовые бытовые слова (одежда/обувь/мех/ткани/
  шины/двери/лакокраска/бытовая техника); для редких предметов вне словаря
  по-прежнему нужна семантическая модель в `models/` (режим `qdrant`).
- **Лексически нерешаемые кейсы** (эксп. 11): зафиксированы как ограничение,
  «костыли» под них не добавлялись — ни слов в словарь мостов, ни пинов кодов,
  ни правок порога под отдельный запрос. Проверено на артефакте v3:
  * **«Настольная лампа»** → 27.40.1 «Лампы накаливания…», ожидалось 27.40.22
    «Светильники … настольные» (`review`, сырая 0.231). Запрос несёт и
    «настольн-», и «ламп-», то есть ровно наполовину ложится на обе позиции;
    лексика не отличает бытовую лампу от светильника.
  * **«Компьютер настольный»** → 26.20.11 «Компьютеры портативные…», ожидалось
    26.20.14 (`review`, сырая 0.228; строка помечена `disputed`). Позиция
    26.20.14 в каталоге есть, но звучит как «Машины вычислительные… поставляемые
    в виде систем» — слова «настольный» в ней нет, поэтому лексический отбор
    уходит к портативным.
  * **«Смарт-часы»** → 26.12.3 «Карты со встроенными интегральными схемами»
    (`review`, сырая 0.206; строка `disputed`). Ложный друг «смарт-» тянет к

  * **«Люстра потолочная»** → 27.40.25 «Люстры … подвесные», ожидалось 27.40.22
    (`review`, сырая 0.519; строка `disputed`). Позиция существует, но каталог
    относит её к другому коду, чем разметка: вердикт — за специалистом по
    нацрежиму (см. `eval/docker-target-checklist.md`).
  Общий вывод: эти промахи — не про пороги и не про словарь, а про отсутствие
  семантики (смысл «лампа ≠ светильник», «часы ≠ карта»). Лечение — включить
  `CLASSIFIER_BACKEND=qdrant` с моделью в `models/` (bge-m3) и переснять свип
  порога для семантических скоров (`eval/docker-target-checklist.md`, раздел D).
- Шкала `confidence` откалибрована (эксп. 10), но опирается на площадку из
  курируемых слов и OOV-проб: на «хвостах» (сырая уверенность 0.165–0.22)
  отображаемая вероятность оптимистичнее реальной точности, а сырые пороги
  `ok`/`review` откалиброваны на более трудном синтетическом распределении —
  поэтому статус `review` и высокая отображаемая уверенность встречаются вместе.
- Спорные пары позиций (ноутбук: прил. 2 vs 3; телевизоры 26.40.20.*) оцениваются
  по группе кода, конкретное приложение выбирает специалист (`clause_ref`
  перечисляет варианты).
- Нагрузочный замер (`eval/api-load-test.md`) сделан в sandbox; замер на
  ML-модели и ноутбуке жюри — по чек-листу `eval/docker-target-checklist.md`.

## Эксперимент 15: семантический режим против лексики на одном наборе

18 строк, где каталог промолчал при существующем коде, и 13 ложных подсказок вне перечня —

| Причина | Строк | Что происходит |

| `threshold_loss` | 5 | верный кандидат на 2-м месте, низкая сырая уверенность режет его порогом |
| смогла семантика | 2 | «игрушка детская», «свитер трикотажный» |

Разбивка по вердиктам: из **9 регрессий** — 7 «поиск не нашёл» и 2 «порог»; реранкер не сломал
ни одной регрессии, он лишь выбирал из того, что дала семантика. В блоке `both_miss` картина
обратная: 5 из 12 строк реранкер **вытягивает** (например «Счетчик воды крыльчатый» → 26.51.63.120,
«Станок токарный с ЧПУ» → 28.41.2, «Судно прогулочное» → 30.12), хотя верный код там был лишь
на 6-м и ниже месте. Итог: реранкер обучен под лексический поиск, на семантических кандидатах
его `evaluate()` не работает, а на лексических — работает; поэтому падение распределяется
примерно 70/30 между качеством поиска и несогласованностью порогов, а не между «поиск против
реранкера».

**Ложные подсказки вне перечня.** Из 13 семантика гасит 2 (USB-флеш, гриль угольный — там сырой
скор 0.49–0.50 тонет под порогом `review`), а 11 остаются; то есть её собственный «тормоз»
не помогает и от ложных друзей. Это подтверждает вывод эксп. 14: тишину надо чинить точечно,
а не сменой модели.

Причина провалов первой группы — знание домена: лексический каталог выигрывает за счёт
нормализации pymorphy3, IDF-весов и курируемых мостов `ml/lexicon.py`, связывающих бытовое
слово с позицией перечня.

**Почему `reranker_loss` — это структурная дыра, а не случайность.** У модели пар
(`ml/reranker.py`, `FEATURE_NAMES`) **нет признака семантического сходства**: все 15 признаков
лексические (`lexical_score`, `idf_coverage`, `char_cosine`, `phrase_match`, …). Поле
`retrieval_score` кладётся в `RankedCandidate` (`classifier.py`, строка 414) и доезжает только
до групповой модели в виде `retrieval_margin` — то есть влияет на *отрыв*, но не на *само*
подтверждение кандидата. Замер на двух строках: «Счетчик воды крыльчатый» — верная позиция
26.51.63.120 стоит первой в семантике, `lexical_score = 0.242`, `idf_coverage = 0.577`, а
`pair_probability = 0.0` у **всех** кандидатов; итог `evaluate()` — `raw = 0.1281`,
`status = not_found` при пороге 0.165. «Станок токарный с ЧПУ» — то же самое (`raw = 0.0835`
при верном коде на первом месте). Семантическое сходство там не слабое, оно просто не подано
модели. Это тот же класс дефекта, что эксп. 12 (`retrieval_score = 0.0` в лексике): признак
дается пайплайном, но теряется до решающей ступени. Настоящий фикс — добавить семантический
скор в `FEATURE_NAMES` и переобучить обе ступени на семантических кандидатах; это уже
отдельный эксперимент, а не правка на ходу.

**Решение.**
1. Режим по умолчанию остаётся `catalog` (`CLASSIFIER_BACKEND=catalog`): семантика в текущем
   виде не улучшает ни top-1, ни разумную цену — она меняет профиль ошибок и стоит ×4 по
   латентности.
2. Ложные подсказки вне перечня семантикой целиком **не лечатся** (2 из 13) — значит гипотеза
   «проблему тишины решит bge-m3» из эксп. 14 закрыта как не подтверждённая; гейт тишины надо
   чинить точечно (разбор ложных друзей — задача роли 2).
3. Семантика остаётся вторым режимом под флагом, а не претендентом на дефолт. Пороги для неё
   нужны свои: свип в `eval/eval_report_qdrant.md` даёт рабочую точку 0.18–0.20 (тишина 91.7-92.6%
   при top-1 77.7-78.9%), а не 0.165.
4. Чтобы семантика стала улучшением, её надо дообучать на парах «название ↔ позиция» (это уже
   другой бюджет и другой риск) либо использовать гибридно — как первый проход только там, где
   лексика даёт низкую сырую уверенность. До этого решения режим не переключаем.
5. Перед любым возвратом к семантике — починить признак: добавить семантический скор в
   `FEATURE_NAMES` (`ml/reranker.py`) и переобучить обе ступени на семантических кандидатах.
   Без этого 7 строк из 23 теряются не по качеству поиска, а по отсутствию входа у модели.

**Границы вывода.** Замер на CPU в Windows-песочнице (Python 3.14), не в Docker и не на
ноутбуке жюри; положение порогов в семантике и абсолютная латентность на целевой машине могут
отличаться. Вывод о качестве («верного кода нет в шортлисте») от среды не зависит и переносится.

## Эксперимент 16: пороги `ok`/`review` под семантическую шкалу

**Зачем.** Артефакт `models/reranker.json` хранит точку, снятую на лексическом бэкенде
(`ok` 0.77, `review` 0.165, эксп. 14). Семантический бэкенд отвечает в другой части той же
сырой шкалы (эксп. 15), поэтому пороги для него надо измерить отдельно — переобучение для
этого не нужно, пороги читаются на лету.

**Инструмент.** `eval/threshold_sweep.py`. Ключевое наблюдение, из которого он вырос: **статус
решается по сырой уверенности**, поэтому сетку порогов можно посчитать без повторных прогонов
модели — один проход по 274 строкам сохраняет `confidence_raw` каждой строки
(`eval/threshold_sweep_<backend>.csv`), а любая пара порогов потом считается пересчётом.
Прежний `run_eval.py --sweep` для каждой точки классифицировал набор заново и двигал только
`review`.

**Что показала сетка 10×11 (мгновенный пересчёт по сохранённым сырым значениям).**

Первое и неожиданное: **`ok` не влияет ни на одну измеряемую метрику**. При фиксированном
`review = 0.165` точки `ok` от 0.30 до 0.90 дают ровно одно и то же: покрытие 90.4%, top-1 среди
отвеченных 88.0%, точность молчания 89.8%, 132 верных подсказки, 11 ложных. Это не ошибка
измерения: `ok` — это порог между `review` и `ok`, а «отвечено» определяется порогом `review`,
поэтому `ok` меняет только то, сколько ответов помечено уверенными. Выбор `ok` — вопрос
политики меток, а не качества, и его нельзя «откалибровать по метрикам».

Всё решает `review` (при `ok = 0.30`):

| `review` | покрытие | top-1 среди отвеченных | точность молчания | верных | ложных |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.165 (артефакт) | 90.4% | 88.0% | 89.8% | 132 | 11 |
| 0.200 | 88.6% | 87.8% | 92.6% | 129 | 8 |
| **0.250** | **82.5%** | **89.8%** | **97.2%** | 123 | **3** |
| 0.300 | 77.1% | 93.0% | 97.2% | 119 | 3 |
| 0.350 | 77.1% | 93.0% | 97.2% | 119 | 3 |

Выбран `review = 0.25`: колено кривой, где ложные подсказки падают 13 → 3 из 108, а top-1 среди
отвеченных даже растёт (88.0% → 89.8%) — дальше растёт только за счёт отказа отвечать.
`ok = 0.77` выровнен по лексике сознательно: он не двигает метрики и означает «уверенный ответ»,
а менять смысл метки без выигрыша незачем.

**Фронтиры двух бэкендов** (при одинаковой точности молчания — лучшее покрытие):

| точность `not_found` | catalog: покрытие / top-1 | qdrant: покрытие / top-1 |
| ---: | ---: | ---: |
| 97% | 80.1% / 94.7% | 82.5% / 89.8% |
| 92% | 89.2% / 91.2% | 89.8% / 87.9% |
| 88% | 91.6% / 91.4% | — (89.8% при 90.4% покрытия) |

На равной точности молчания каталог по-прежнему лучше и по покрытию, и по top-1 — то есть
семантика остаётся недоминируемой альтернативой, а не заменой. Итоговая цена переключения:
**−15 верных подсказок за −10 ложных** (139 → 123 против 13 → 3), плюс ×4 латентности.

**Гибридная маршрутизация проверена и отклонена как гипотеза.** По уже снятым числам
(`eval/backend_comparison.csv`) просчитаны правила «если лексика неуверена — спросить семантику»:
при сыром пороге 0.20–0.25 маршрутизация даёт 237 верных против 234 у чистого каталога,

**Что изменено в коде.**

дороже — 10 лишних ложных подсказок или 15 потерянных верных.



## Эксперимент 17: векторные признаки доходят до решения (2026-10-23)

**Проблема.** В отгруженном `ml/artifacts/reranker.json` веса `dense_cosine`/`dense_gap` равны 0.0,
артефакта `reranker.<тег-эмбеддера>.json` в репозитории не было, поэтому векторный поиск только
пополнял список кандидатов. `--dense --gate` такой артефакт обучать умел, но **удалял**: правило
сравнивало *округлённые проценты* через `new >= base`, и падение `ok_precision` на одну строку
(131/143 → 133/146, то есть −0.5 п.п. при +2 верных ответах) перевешивало рост top-1 на 1.8 п.п.
Гейт не печатал, какая метрика не прошла, — решение было необъяснимым.

**Что измерено** (274 строки: 166 с кодом, 108 «вне перечня»; эмбеддер tfidf, seed 1875,
артефакты воспроизводятся `scripts/build_model.py`):

| Метрика | Лексика | Вектор | Δ строк | Итог |
| --- | ---: | ---: | ---: | --- |
| верный `not_found` | 92/108 (85.2%) | 92/108 (85.2%) | 0 | равно |
| точные названия, top-1 | 112/112 | 112/112 | 0 | равно |
| top-1 (с кодом) | 137/166 (82.5%) | 140/166 (84.3%) | **+3** | лучше |
| top-3 (с кодом) | 145/166 (87.3%) | 149/166 (89.8%) | **+4** | лучше |
| top-1 по всем | 229/274 (83.6%) | 232/274 (84.7%) | **+3** | лучше |
| точность `ok` | 131/143 (91.6%, 12 неверных) | 133/146 (91.1%, 13 неверных) | +1 неверный | в допуске |

**Правило допуска (реализовано в `eval/dense_gate.py`, 16 тестов в `api/tests/test_dense_gate.py`).**
Сравнение идёт по строкам, а не по процентам: на 166/274 строках одна строка — это 0.6/0.4 п.п.,
и процент, посчитанный на подмножестве, которое выбирает сама модель, шумит сильнее, чем различает.

* `correct_silence`, `exact_top1` — жёсткие: ни одной строки нельзя потерять;
* `top1_expected`, `top3_expected`, `top1_all` — потеря не более одной строки, и хотя бы одна
  метрика должна выиграть хотя бы строку (иначе «не хуже» — это не повод что-то менять);
* `ok_precision` — по числу неверных уверенных ответов, допуск +1 строка;
* `ECE` — не хуже базы более чем на 0.01.

**Вторая найденная проблема: база сравнения была чужой.** Гейт брал `models_dir/reranker.json`,
то есть в образе — отгруженный файл, а он **не воспроизводится текущим тренером**: в нём 29277 пар,
пороги 0.621/0.097 и нет `split_strategy`, тогда как текущий код даёт 27858 пар и 0.306/0.227.
Сравнение свежего кандидата с ним мерило разницу рабочих точек, а не вклад векторов. Теперь база
обучается в том же прогоне (`--baseline-artifact` оставляет возможность сравнить с внешним файлом,
но тогда ответственность за его происхождение на вызывающем). Отчёт `dense-gate.json` хранит
sha256 обоих артефактов и флаг `baseline.trained_in_run`.

**Третье: дрейф отгруженного tfidf-эмбеддера.** `ml/artifacts/tfidf_embedder.json` был подогнан
2026-10-18, до чистки каталога (11 OCR-исправлений): `doc_frequencies` отличались, меняя векторное
пространство под всеми tfidf-артефактами. Файл переподогнан по текущему каталогу, тест
`test_shipped_tfidf_embedder_is_fitted_on_the_current_catalog` ловит такое расхождение.

**Что теперь в репозитории.** `ml/artifacts/reranker.tfidf.json` (вес `dense_cosine` 0.353,
`dense_gap` 2.121) и `ml/artifacts/dense-gate.json` с вердиктом ПРИНЯТ. Проверка на живом пути
(`EMBEDDER_BACKEND=tfidf VECTOR_SEARCH=true python eval/run_eval.py`): 84.3 / 89.8 / 85.2 / 84.7,
ECE 0.036 — то есть признаки действительно участвуют в решении, а не только в шортлисте.

**Воспроизводимость.** Лексический артефакт воспроизводится байт в байт (две независимые полные
сборки дали один sha256 `e1f3d8cf…`), а векторный — нет: два прогона дали 38012 и 38010 обучающих
пар, `dense_cosine` 0.35271 и 0.35267, sha `ac0f46fd…` и `ef4625…`. Разница появляется в шортлисте
кандидатов (порядок сложений в BLAS-скалярных произведениях), поэтому число пар, попавших в
обучение, слегка гуляет. На размеченном наборе это не видно: оба артефакта дают одинаковые числа
до строки (проверено отдельным прогоном гейта на `ef4625…`). Практический вывод: гейт сверяет
**метрики**, а не sha, а отчёт хранит sha проверенного файла, чтобы можно было понять, что именно
оценивалось. `tfidf_embedder.json` при этом не байт-идентичен между сборками только из-за поля
`trained_at` — частоты документов совпадают (это и проверяет тест).

**Отрицательный контроль.** Тот же гейт на том же артефакте с обнулёнными весами `dense_*`
(то есть «векторные признаки не работают») отклоняет его и удаляет файл:
top-1 137 → 132 строки, top-3 145 → 139, ECE 0.053 → 0.113 (плюс «ни одна ключевая метрика не
улучшилась»). Диагностика печатается в лог сборки и остаётся в `dense-gate.json`, поэтому
причина отказа видна без повторного прогона. Повторный прогон гейта на принятом артефакте дал
те же числа до строки — вердикт не зависит от того, какой лексический файл лежит в каталоге.

**Что осталось на тот момент.** Отгруженный `ml/artifacts/reranker.json` был оставлен как есть
(87.3% top-1 при 74.1% тишины против 82.5% при 85.2% у пересборки тем же кодом), а CI-пороги
`--min-top1 85 --min-top3 91` краснели на любой честной пересборке. Оба вопроса закрыты в
эксп. 19 (артефакт и откат) и эксп. 20 (CI-гейт); сравнение «на равной тишине», которое решило
вопрос, — в эксп. 18.

## Эксперимент 18. Сравнение при равной тишине, а не при равном пороге (2026-10-23)

**Проблема.** «У старого артефакта top-1 выше» — верное наблюдение и неверный вывод. У каждого
артефакта своя шкала откалиброванной уверенности и свой порог, поэтому одинаковое число порога
означает разные рабочие точки: отгруженный файл отвечает на 189 строках из 274, пересборка — на
163, векторный — на 166. Сравнивать проценты на разных знаменателях бессмысленно, а `top-1`
считается по `response.code`, то есть молчание автоматически делает строку неверной.

**Инструмент.** `PYTHONPATH=api python eval/pareto.py [--detail] [--extra имя=путь[:dense]]`
(`eval/pareto.py`): для каждого артефакта берёт его собственные уверенности как сетку порогов,
считает полный набор метрик на каждом и печатает таблицу «при тишине не ниже N — самый
разговорчивый порог, который её ещё держит». Правило выбора: среди точек, проходящих бюджет
тишины, побеждает та, что даёт больше верных кодов; при равенстве — та, что отвечает чаще.

**Измерено** (274 строки, эмбеддер tfidf, 13–15 точек на артефакт):

| Тишина ≥ | лексика | вектор | старый файл (`ce0fb5f2…`) |
| ---: | ---: | ---: | ---: |
| 70 / 75 / 80 % | 84.3 % (140/166), порог 0.616 | **87.3 % (145/166)**, порог 0.475 | 87.3 % (145/166), порог 0.130 |
| 85 % | **84.3 % (140/166)**, порог 0.616 | **84.3 % (140/166)**, порог 0.655 | 81.3 % (135/166), порог 0.247 |
| 90 % | 82.5 % (137/166) | **84.3 % (140/166)**, порог 0.655 | 81.3 % (135/166) |

Своя рабочая точка каждого:

| Артефакт | Порог `review` | Тишина | top-1 (с кодом) | top-3 | top-1 по всем | ECE | Ответов |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `reranker.json` (лексика) | 0.684 | 85.2 % (92/108) | 82.5 % (137/166) | 87.3 % (145/166) | 83.6 % (229/274) | 0.053 | 163 |
| `reranker.tfidf.json` (вектор) | 0.621 | 85.2 % (92/108) | **84.3 % (140/166)** | **89.8 % (149/166)** | **84.7 % (232/274)** | **0.036** | 166 |
| старый `reranker.json` (снят) | 0.130 | 74.1 % (80/108) | 87.3 % (145/166) | 93.4 % (155/166) | 82.1 % (225/274) | 0.102 | 189 |

**Вывод.** Старый файл не лучше — он громче: при равной тишине он не превосходит пересборку
тем же кодом, а на рабочей тишине 85 % проигрывает 5 строк. Его 87.3 % — это следствие порога,
который отвечает на 23 строки чаще и на 12 запросах «вне перечня» даёт ложную подсказку вместо
честного `not_found`. Калибровка хуже в 2–3 раза (ECE 0.102 против 0.036).

**Решение по рабочей точке.** Оставляем пороги артефактов (`review` 0.621 / 0.684): на уровне
тишины 85 % векторный артефакт не доминируется ничем, а более тихий режим (тишина ≥ 95 %)
поднимает top-1 по всем до 86 % ценой ~15 верных подсказок — это продуктовый выбор, и он
доступен без пересборки: `CATALOG_REVIEW_FLOOR` / `CATALOG_OK_FLOOR` (окно проверяет
`OK > REVIEW` и откатывает пару, если она вырождена).

**Проблема.** `ml/artifacts/reranker.json` был файлом, который текущий тренер не воспроизводит:
29277 обучающих пар, пороги `ok=0.840 / review=0.130`, ECE 0.102, ни `split_strategy`, ни

старый файл нельзя было ни объяснить, ни перемерить, ни безопасно заменить.

**Что сделано.**

* `reranker.json` заменён пересборкой текущим кодом: sha256 `e1f3d8cf…`, две независимые полные

## Эксперимент 20. CI: регрессия против записанного замера вместо порогов (2026-10-23)

**Проблема.** В workflow были вморожены пороги `--min-top1 85 --min-top3 91 --min-silence 80`
с комментарием «измерено: top-1 86.1 / top-3 92.2 / silence 81.5, минус одна строка». Эти числа
принадлежали артефакту 2026-09, который не воспроизводится (эксп. 19): честная пересборка даёт
82.5 / 87.3 / 85.2, поэтому job `quality` был красным на каждом прогоне — и красным по причине,
которой нет в коде. Порог на **долю** к тому же имеет разрешение одну строку: на 166 строках это
0.6 п.п., на 108 — 0.9 п.п., то есть «минус одна строка» и «порог 85» не одно и то же.

**Что сделано.**

* `eval/quality_gate.py` — правило: каждая метрика может потерять **одну строку**, `ok_precision`
  сравнивается по числу неверных уверенных ответов (его знаменатель выбирает модель), ECE не может
  вырасти больше чем на 0.01, разное число строк в замере — это ошибка, а не регрессия.
  Всё в одном отчёте: таблица «база / сейчас / Δ строк», причины отказа перечисляются вместе.
* `eval/baselines/lexical.json` и `eval/baselines/dense-tfidf.json` — замеры двух конфигураций
  с провенансом: backend, эмбеддер, артефакт и его sha256, порог `review`, число строк.
  Пишутся `eval/run_eval.py --report`, сравниваются `--baseline`; обновление — коммит с
  объяснением, само ничего не обновляется.
* CI меряет **обе** конфигурации: откат (`VECTOR_SEARCH=false` → `reranker.json`) и боевую
  (`VECTOR_SEARCH=true`, tfidf → `reranker.tfidf.json`). Это 17 с на конфигурацию против 6 минут
  у прежнего шага, который ещё и гонял свип.

**Записанные базовые линии (274 строки):**

| Конфигурация | top-1 (с кодом) | top-3 | верный `not_found` | точные названия | `ok` | ECE |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `lexical.json` | 137/166 | 145/166 | 92/108 | 112/112 | 131/143 | 0.0534 |
| `dense-tfidf.json` | 140/166 | 149/166 | 92/108 | 112/112 | 133/146 | 0.0356 |

**Отрицательный контроль.** Синтетическая «слишком сильная» база (top-1 145/166, тишина 96/108,
ECE 0.010) роняет прогон с кодом 1 и печатает всё сразу: «верный not_found: 92 из 108 против 96
(−4 строки, допуск 1); top-1 (с кодом): 140 из 166 против 145 (−5); ECE вырос 0.010 → 0.036».
Тест `api/tests/test_quality_gate.py` (15 тестов) фиксирует границы: одна потерянная строка —
шум, две — регрессия, плюс 0.01 ECE проходит, плюс 0.011 — нет.

## Эксперимент 21. Автокоррекция подменяет настоящие слова — исправлено, но не отгружено (2026-10-24)

**Как нашли.** При разборе 16 «тихих» промахов понадобилось увидеть сырую уверенность
на `not_found` (в ответе она обнуляется по контракту), поэтому `LogisticReranker.evaluate`
обернули шпионом. В шпион пришло `«Платье женское лесного»` вместо «Платье женское летнее»:
`ml/fuzzy.autocorrect` подменял слово, которое есть в запросе пользователя, на слово из
каталога.

**Причина.** Охранное условие «это настоящее русское слово — не трогать» сравнивало
`pymorphy3.parse(token)[0].score` с 0.6. pymorphy делит вероятность между разборами, поэтому
обычное слово в косвенной форме редко набирает много: «летнее» 0.50, «садовый» 0.50,
«корм» 0.50, «складной» 0.10. Все они проходили как «возможная опечатка» и заменялись на
ближайшее слово каталога: «Платье женское летнее» → «… лесного», «Грабли садовые» →
«… судовые», «Корм для собак» → «корда для собак», «Зонт складной» → «зонды складной».
Затронуто **9 из 274** размеченных запросов — и это не только ответ: подмена входит в
retrieval и во все признаки реранкера, то есть модель видела другой товар.

**Замена.** `Parse.is_known` — «эта словоформа есть в морфологическом словаре». Опечатки

код). Это исправление корректности и воспроизводимости, а не источник прибавки.

**Почему не в этом PR.** Артефакт обязан воспроизводиться из текущего кода: CI-шаг

## Эксперимент 22. Канал подсказок при `not_found` был мёртв (2026-10-24)

**Наблюдение.** 108 строк «позиции нет в перечне» и 16 верных по коду строк, ушедших в
тишину, получали `alternatives: []` — специалист не видел ни одной зацепки. При этом 10 из
этих 16 промахов имели **верный код на первом месте** ранжирования: ранжирование знало
ответ, ответ его выбрасывал.

**Причина.** `_distinct_alternatives` для `not_found` оставлял кандидатов с
`probability >= threshold_review`. Но `threshold_review` — порог **групповой** уверенности,
а `probability` — парная вероятность: разные шкалы. Хуже того, `not_found` по определению
означает «групповая уверенность ниже порога», поэтому условие не могло выполниться никогда.
Срабатывало только особое ветвление «победитель без кода ОКПД2» — единственный источник
непустых подсказок.

**Правило вместо порога.** Подсказка при `not_found` остаётся, если позиция **лексически
зацеплена** за запрос: есть общий содержательный стем (стемы мостов тоже считаются — это
осознанное решение лексикона). «Ложный друг», похожий только векторно, и бессмысленный
запрос («qwerty zxcvbn asdf») подсказок не дают: придумывать зацепку хуже, чем молчать.
Демотированная позиция без кода — не тишина (запрос попал в каталог), поэтому её
раннер-апы остаются без фильтра, как раньше.

**Измерено** (`eval/baselines/*.json` перезаписаны, остальные метрики не двигаются):

| Конфигурация | top-3 до | top-3 после | подсказок на `not_found` |
| --- | ---: | ---: | --- |
| `reranker.json` (откат) | 145/166 | **149/166** | 38 из 92 |
| `reranker.tfidf.json` (боевая) | 149/166 | **152/166** | 38 из 92 |

Top-1, тишина и `ok` не изменились: подсказка — не ответ, `status` остаётся `not_found`.
Тесты: `api/tests/test_contract_invariants.py::test_not_found_keeps_lexically_anchored_leads`,
`::test_not_found_returns_no_hint_when_nothing_is_anchored`.

## Эксперимент 23. «Сигнал отсутствия класса» в перечне: почему его нельзя обучить (2026-10-24)

**Задача.** 13 уверенных (`ok`) ответов не совпадают с ожидаемым кодом, 5 из них —
на товары, которых в перечне нет вовсе («Принтер лазерный», «Шредер для бумаги»,
«МФУ лазерное», «USB-флеш накопитель», «Конструктор детский»). Гипотеза: нужен
отдельный признак «класса нет в каталоге», после чего порог можно опустить и забрать
16 строк, ушедших в тишину при верном кандидате.

**Что измерено до всякой правки** (боевой артефакт, 274 строки). Сигналы по классам:

| класс | n | покрытие «своих» слов запроса | доля слов вне словаря каталога | ответ через мост |
| --- | ---: | ---: | ---: | ---: |
| уверенные `ok` и верные | 133 | 0.69 | 0.12 | 35 % |
| уверенные `ok` и неверные | 13 | 0.42 | 0.29 | 46 % |
| из них «вне перечня» (5) | 5 | **0.10** | **0.47** | **80 %** |
| из них спорные/соседний код (8) | 8 | 0.62 | 0.19 | 25 % |
| верный код есть, но тишина | 16 | 0.44 | 0.27 | **0 %** |
| верная тишина | 92 | 0.24 | **0.68** | 3 % |

Разделение есть: у ложных уверенных ответов почти нет пересечения с названием позиции
(0.10), а у настоящей тишины почти все слова вне словаря каталога (0.68).

**Попытка 1 — признаки в модели уверенности.** Добавлены `top_own_cover` и
`query_oov_share` (и вариант с `top_product_absent`), пересобраны артефакты:

| вариант | top-1 | top-3 | тишина | неверных `ok` |
| --- | ---: | ---: | ---: | ---: |
| отгружено | 137/166 | 149/166 | 92/108 | 12/143 |
| + `own_cover`, `oov`, `product_absent` | 139/166 | 151/166 | **89/108** | — |
| + `own_cover`, `oov` | 138/166 | 150/166 | **91/108** | — |

Тишина падает: модель выучила **положительный** вес на «ответ через мост»
(`top_product_absent` +0.49). Причина не в признаках, а в данных: обучающие пары
строятся из названий каталога, поэтому «класса нет в перечне» в них не бывает ни
разу — мост там всегда ведёт в верную позицию. Отрицательный пример надо придумывать.

**Попытка 2 — правило вместо модели.** «Мост сработал и своих слов в каталоге нет ⇒
не отвечать»: убирает 5 ответов на отсутствующий класс, но **стоит 24 верных**
(«Костюм мужской» → 14.1, «Цемент 500» → 23.51, «Сапоги детские» → 15.2, «Окна
пластиковые», «Витрина холодильная»…). Дешевле: «голова запроса вне словаря и без
моста» — теряет 1 верный («Автобус для перевозки 10 человек») и убирает 3 ответа
(все `review`, не `ok`). Это перестановка рабочей точки, а не решение.

**Попытка 3 — мост только по голове запроса.** В лексиконе нашёлся самомост
`"бумага": "бумага"`: он даёт +0.15 к позиции «Бумага и картон» любому запросу со
словом «бумага» и взвинчивает `bridge_cover`. Результаты при текущем артефакте:

| лексикон | top-1 | top-3 | тишина | неверных `ok` |
| --- | ---: | ---: | ---: | ---: |
| как есть | 140/166 | 152/166 | 92/108 | 13/146 |
| без самомоста | 134/166 | 148/166 | 93/108 | 11/133 |
| мост только по голове запроса | 139/166 | 151/166 | 93/108 | 11/143 |

«Шредер для бумаги» в обоих вариантах уходит в тишину — баг настоящий, но цена
(1–6 верных ответов за 1 строку тишины) выше выигрыша.

**Вывод.** Отказ «класса нет в перечне» не отделяется лексическими сигналами от
«обобщающая позиция перечня покрывает товар»: это одна и та же механика, различие —
решение специалиста по конкретной позиции, а не свойство текста. Пока в разметке
«Костюм мужской» → 14.1 «Одежда» верно, а «Конструктор детский» → 32.4 «Игры и
игрушки» — «вне перечня», любая модель, выучившая второе, разучится первому.

Инструмент для разбора: `PYTHONPATH=api python eval/review_errors.py` — делит
неверные ответы по механике и показывает, какие из них размечены противоположным
образом. На 274 строках: 3 «соседний код» (Конвектор 25.21.11.150/160, Скрипка
32.20.12.111/110, Лыжи 32.30.11.110/120), 5 «мост + обобщающая позиция» (и ни одной
верной строки с этой механикой), 1 «мост, но спорно» (Монитор), 17 прочих (11 из них
`review` на отсутствующий класс).

## Эксперимент 24. Автокоррекция подменяла настоящие слова (исправлено и отгружено) (2026-10-24)

**Как нашли.** При разборе «тихих» промахов понадобилось увидеть сырую уверенность на
`not_found` (в ответе она обнуляется по контракту), поэтому `LogisticReranker.evaluate`
обернули шпионом. В шпион пришло `«Платье женское лесного»` вместо «Платье женское летнее»:
`ml/fuzzy.autocorrect` подменял слово, которое есть в запросе пользователя, на слово из
каталога.

**Причина.** Охранное условие «это настоящее русское слово — не трогать» сравнивало
`pymorphy3.parse(token)[0].score` с 0.6. pymorphy делит вероятность между разборами, поэтому
обычное слово в косвенной форме редко набирает много: «летнее» 0.50, «садовый» 0.50,
«корм» 0.50, «складной» 0.10. Все они проходили как «возможная опечатка» и заменялись на
ближайшее слово каталога:

| запрос специалиста | что уходило в retrieval |
| --- | --- |
| Платье женское летнее | Платье женское **лесного** |
| Грабли садовые | Грабли **судовые** |
| Корм для собак | **корда** для собак |
| Зонт складной | **зонды** складной |

Затронуто **9 из 274** размеченных запросов. Подмена входила не только в ответ, но и в
retrieval и во все признаки реранкера — модель видела другой товар. Хуже: **11 из 27**
шумовых слов, которыми тренер разбавляет обучающие запросы, старый критерий считал
опечатками — «мужской» (0.33), «стальной» (0.29), «новый» (0.56), «бытовой» (0.54),
«настольный» (0.50). То есть испорчена была и обучающая выборка.

**Замена.** `Parse.is_known` — «эта словоформа есть в морфологическом словаре». Опечатки
(«Монитр», «Клавитура», «Бумга», «Дрел») — ровно те токены, которых в словаре нет; настоящие
слова есть всегда. Зависимость от версии `pymorphy3-dicts-ru` при этом исчезает. Названия
каталога (112 / 112 точных запросов) не коверкались ни старым, ни новым критерием — баг бил
только по живой речи.

**Почему это не отгружалось сразу.** Артефакт обязан воспроизводиться из текущего кода, а
пересобранный векторный артефакт терял одну строку тишины и `dense_gate` его отклонял.
Разбор показал, что вердикт гейта — лотерея разбиения, и это отдельный вывод (ниже).

**Измерено по сидам** (одна и та же кодовая база, 274 строки):

| seed | тишина, лексика | тишина, вектор | top-1, лексика | top-1, вектор | top-3, лексика | top-3, вектор | гейт |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1875 | 93 | 92 | 137 | 140 | 149 | 152 | отклонён (−1 тишина) |
| 1876 | 88 | 91 | 142 | 142 | 154 | 154 | принят |
| 1877 | 93 | 91 | 139 | 140 | 151 | 152 | отклонён (−2 тишина, ECE) |

Тишина лексического артефакта гуляет на **5 строк** от сида к сиду. При нулевом допуске это
значит, что один и тот же фикс принимается или отклоняется броском монеты — что и произошло.
Поэтому гейт получил режим `--gate-seeds`: счётчики прогонов складываются, допуск на строку

88.9 % верной тишины вместо 85.2 % (+4 строки) и 86.1 % top-1 по всем. Выглядит как
бесплатное улучшение, но порог выбран **на том же наборе, которым мы меряем** — это подгонка
под 274 строки, а не измерение. Чтобы взять эту точку, нужен независимый набор или отдельный

## Эксперимент 26. Порог `review` на размеченном наборе подбирать нельзя (2026-10-24)

**Вопрос.** В свипе (`eval/eval_report.md`) видна клетка `review = 0.655`: те же 84.3 % top-1
и 91.6 % top-3, что у 0.622, но 88.9 % верной тишины вместо 85.2 % (+4 строки) и 86.1 %
top-1 по всем. Это реальная рабочая точка или подгонка под те же 274 строки?

**Инструмент.** `eval/threshold_cv.py`: ранжирование от порога не зависит (он решает только
«ответить или промолчать»), поэтому дорогое считается один раз, а метрики пересчитываются для
любой сетки мгновенно. Дальше — честная процедура: 5 фолдов × 20 повторов, порог выбирается
**на обучающих фолдах**, метрики снимаются **на отложенных**. Сверка с отчётом: при 0.622
инструмент даёт 140/152/92/232 — ровно то же, что `run_eval.py`.

**Что видно на всём наборе.** Максимум «top-1 всего» = 237 достигается на порогах
**0.66…0.75** — это плато из четырёх точек, а не одна заветная клетка. Направление обмена
реально: выше порог — больше тишины, меньше ответов.

**Что видно вне выборки** (строки на фолд, фолд ≈ 55 строк):

| цель выбора | top-1 | тишина | top-1 всего | медиана выбранного порога |
| --- | ---: | ---: | ---: | ---: |
| порог артефакта (0.622) | 28.0 | 18.4 | 46.4 | — |
| `top1_all` | 26.9 | 19.8 | **46.6** | 0.753 (разброс 0.656…0.784) |
| `top1_guarded` (тишина ≥ 90 %) | 27.3 | 19.7 | **47.0** | 0.736 (0.656…0.780) |

Прирост **+0.2…+0.6 строки на фолд** (≈ +1…3 на весь набор) при разбросе выбранного порога
0.66…0.78 и полном несовпадении с порогом артефакта (0 из 100 фолдов). Это шум выбора:
настоящий эффект в 4–5 строк, который виден на всём наборе, почти целиком объясняется тем, что
клетку выбирали на тех же строках, которыми мерили.

настройкой. Предупреждение в логе перевёрнуто: теперь оно срабатывает не на «порог не от
артефакта», а на **порог ниже измеренного** — то есть на конфигурацию, которая отвечает чаще,
чем измерено безопасно.

(в каждой корзине точность выше заявленной уверенности). Причина та же: Platt-карта
подбиралась, когда треть строк «вне перечня» была размечена поиском по `data.csv`. Гейт
допуска (ECE не хуже +0.01) поэтому считает пару «лексика → вектор» регрессией по ECE, хотя по
top-1 и top-3 вектор впереди (+3 и +7 строк). Переобучение карты — отдельная работа с моделью,

### Часть 2. Почему вырос ECE: платформа калибровки спорила с лексиконом

Карта уверенности (Platt) подбирается на отдельной платформе — «товарные слова из
`BRIDGES` + пробы вне перечня» — и не видит размеченный набор. После волны гейт по пулу
четырёх прогонов отклонил векторный артефакт по одной строке: ECE 0.085 → 0.121 при допуске
+0.01. При этом все остальные метрики выросли (top-1 753 → 765 из 804, top-3 775 → 792,
тишина 121 → 122, `ok` 682/703 → 693/712).

Диагностика (артефакт фиксирован, карта переподбиралась без переобучения модели):

| | платформа | размеченный набор (оцениваемые отвеченные) |
| --- | ---: | ---: |
| точность | 0.847 (481/568) | 0.970 (193/199) |
| средняя сырая уверенность | 0.911 | — |
| ECE без карты (identity) | 0.064 | 0.058 |
| ECE с картой, подобранной на платформе | 0.073 | **0.121** |

Платформа считала модель на 12 п.п. хуже, чем она есть на реальных запросах, и карта честно
сдвигала шкалу вниз на 0.67 логита — то есть на размеченном наборе занижала её. Две причины,
обе — дефекты платформы, а не модели:

1. **Пробы «вне перечня» устарели относительно лексикона.** Восемь из 80 голов
   (`OUT_OF_SCOPE_HEADS`) волна перевела в «в перечне»: клавиатура, сканер, дрель,
   шуруповёрт, флешка, миксер, гантели, колонка. Платформа считала ошибкой каждый верный
   ответ на них — 28 из 44 отвеченных проб. Про «колонку» спор быть не может: в самом
   размеченном наборе есть строка «Беспроводная колонка» → `26.40.42.110`. Модификатор
   `офисный` тоже стал мостом («офисов») и тянул пробы в «Мебель для офисов».
2. **Модификатор, который сам называет позицию.** `специализированные` совпадал с
   «Контейнеры специализированные» и перебивал товарное слово в 9 строках платформы
   («специализированные блокнот» → «Контейнеры специализированные»). Ещё два модификатора
   делили основу со словами каталога.

**Исправление.** (а) `make_negative_queries` выбрасывает голову, если её переводит лексикон,
и любую пробу, в которой есть слово лексикона целиком: «слово, которое лексикон объявил
в перечне, не может быть меткой „молчать“». (б) `CALIBRATION_MODIFIERS` — только стилевые
слова, без общей основы со словами каталога; это закреплено тестом. (в) платформа теперь
сама исключает запросы размеченного набора: четыре источника мостов («квадрокоптер», «пазл»,
«скейтборд», «мангал») — это дословно строки измерения, раньше их отсекал только вызывающий.

Эффект (карта переподобрана, модель та же):

| | до | после |
| --- | ---: | ---: |
| запросов платформы | 918 | 867 |
| отвечено / верно | 568 / 481 (0.847) | 551 / 515 (0.935) |
| подобранная карта | `a=1.0, b=−0.675` | `a=1.0, b=+0.378` |

Та же правка улучшила и сами модели: восемь голов перестали быть противоречивой разметкой

### Часть 3. ECE гейта: пул таблиц надёжности вместо среднего |ECE|

надёжности (`reliability_bins`/`pool_bins` в `eval/dense_gate.py`) и считает ECE по
объединённым корзинам — та же доктрина, что и `pool_counts`: «мерить семейство артефактов,
а не одно разбиение». Среднее по прогонам остаётся в отчёте (`ece_mean_per_run`), так что
решение можно перечитать обоими способами.

## Эксперимент 30. Реальные строки закупки: почему была «яма» review и молчание (2026-10-24)

**Задача.** Специалист прогнал через API два своих выгруза по 100 строк — закупки со
спецификацией после `;` (файл 4) и список офисных товаров (файл 5) — и увидел не «ошибки», а
структуру: 55 строк в `review` и 82 в `not_found` против 63 `ok`. Вопрос: почему модель молчит
и можно ли это починить без нового обучения.

**Воспроизведение.** Оба файла прогнаны локально на отгруженных артефактах
(`EMBEDDER_BACKEND=tfidf`, `reranker.json`, `scoring=lexical-reranker`): **100/100 статусов и
100/100 кодов совпали** с выгрузками (файл 4: 44/29/27, файл 5: 19/26/55). Значит дело не в
окружении и не в Qdrant, а в двух местах конвейера — входном тексте и лексиконе.

### Часть 1. Пять механизмов «ямы»

1. **Спецификация после `;` — не товар.** Строка вида
   `Машина стиральная LG F2J3NS0W; бытовая; загрузка 6 кг; отжим 1000 об/мин` целиком попадала
   в скоринг. Признаки покрытия считают долю известных слов запроса, а `DDR4`, `1000 об/мин`,
   `1 шт` неизвестны по построению — уверенность падала у *правильного* ответа. Обрезка по
   первому `;` давала +25 строк `ok` в файле 4, но теряла 3 кода: у 125 из 1126 названий
   позиций перечня сам `;` внутри («Плита Kronospan MDF; древесно-волокнистая» → без хвоста
   уезжает в `22.21.4`). Отсюда не обрезка, а второй проход.
2. **`review` — это узкая полоса 0.596…0.768, а не «сомнение».** 26 из 29 строк `review`
   в файле 4 содержали верный код. Полоса — свойство калиброванной шкалы группы: между «уверен
   достаточно» и «молчу» лежит всего 0.17, и туда попадают длинные строки с брендами.
3. **Модификатор `офисный` был мостом.** `офисный → офисов` (31.01.1) отправлял в мебель
   `Ламинатор офисный`, `Сервер офисный`, `Степлер офисный`, `Моноблок офисный`,
   `Кофемашину`, `Маршрутизатор`, `АТС`, `Сейф` — 16 строк файла 5, из них 10 не мебель.
   Модификатор говорит о *месте применения*, а не о позиции перечня.
4. **81 семейство позиций с одинаковым названием в разных приложениях.** «Мебель для офисов»
   есть и в приложении 2 (`31.01.1`), и в приложении 3 (`31.01.11/31.01.12`); «Машины офисные
   прочие» — `28.23.23` в прил. 2 и `28.23` в прил. 3. Это неустранимая неоднозначность
   *разметки*, а не ошибка модели: оба кода верны, выбрать «единственно верный» нельзя.
5. **Молчание ≠ промах.** Из 55 молчаний файла 5 около 30 — товары, которых в перечне нет
   вообще (ИБП, картридж, ручка, калькулятор, аптечка, огнетушитель, жалюзи, кулер,
   увлажнитель, органайзер, патч-корд). Это верное поведение: перечень закрытый, а
   «придумать код» хуже, чем промолчать.

### Часть 2. Два бесплатных исправления (без обучения)

**(а) Двухпроходное сравнение строки закупки** (`ml/query.py`, `CatalogClassifier`).
Строка с разделителем `;`/`|` скорится дважды — целиком и только имя до разделителя; ответ
выбирается по калиброванной уверенности, при равенстве побеждает короткий вариант, а в ответе
всегда возвращается исходный текст пользователя. Разделитель внутри спецификации
(«1 шт; 2 кг») именем не считается: голова обязана содержать ≥3 буквы. Пакетный путь
(`classify_many`) кодирует оба варианта одним батчем, у Qdrant оба варианта идут в один
`_search_many`, затем группа сворачивается в один ответ. «Плита Kronospan MDF;
древесно-волокнистая» сохраняет `16.21.14`: полная строка увереннее короткой.

**(б) Волна 4 лексикона**: удалён мост `офисный → офисов`; мебель повешена на *предметы*
(`стул`, `кресло`, `тумба`, `диван`, `банкетка`, `перегородка`, `ресепшн`, `стойка` →
`офисов` = 31.01.1) с вето на медицинские/парикмахерские кресла и кресла-коляски; `стол`
требует письменного/офисного/переговорного контекста, а кухонный стол и шкаф остаются в
`31.02.10` через мост `кухонный → кухонная` (только рядом со `стол`/`шкаф`/`мебель`);
`журнальный → гостиной` (31.09.12); `шкаф` требует металла/документов/одежды, а не «книжный».

## Эксперимент 31. Плотный режим без e5: переключатель и что он реально даёт (2026-10-24)

**Задача.** «Векторные признаки» в проекте — это не «включить Qdrant», а *артефакт
реранкера, обученный под конкретный эмбеддер*. В образе по умолчанию лежит
`intfloat/multilingual-e5-small` (`/opt/models/embedder`), но артефакта под тег e5 в
репозитории нет: он строится шагом `scripts/build_model.py --dense --gate` внутри образа,
где веса доступны. Пока его нет, для e5 работает лексический `reranker.json`, а векторы
только пополняют шорт-лист (это видно в `GET /health/ready` → `vector_search.scoring`).

Поэтому плотный путь проверен на эмбеддере, который считается офлайн и детерминированно —
`tfidf`. Это не «заглушка ради теста»: у tfidf есть свой отгруженный артефакт
`ml/artifacts/reranker.tfidf.json`, прошедший гейт (эксп. 29), и его выбирает
`reranker_artifact_path(tag="tfidf")`.

**Как воспроизвести:**

```bash
EMBEDDER_BACKEND=tfidf VECTOR_SEARCH=false PYTHONPATH=api python eval/run_eval.py   # лексика
EMBEDDER_BACKEND=tfidf VECTOR_SEARCH=true  PYTHONPATH=api python eval/run_eval.py   # плотный
```

**Что измерено (размеченный набор, 201 строка с кодом; после волны 4, эксп. 30):**

| Режим | top-1 | top-3 | тишина | top-1 по всем | точные | ECE |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `VECTOR_SEARCH=false` (`reranker.json`) | 94.5% (190/201) | 97.5% | 96.9% | 94.8% | 112/112 | 0.018 |
| `VECTOR_SEARCH=true` (`reranker.tfidf.json`) | **95.5% (192/201)** | **99.0%** | 96.9% | **95.7%** | 112/112 | 0.029 |

Оба прогона проходят гейт относительно своих баз (`eval/baselines/lexical.json`,
`eval/baselines/dense-tfidf.json`), базы обновлены этими же замерами.

**Чего плотный режим не делает.** На строках пользователя (200 шт.) он даёт
106/32/62 (`ok`/`review`/`not_found`) против 108/29/63 у лексики — то есть **не закрывает
остаточную «яму»**: те же строки (`Внешний жёсткий диск 2 ТБ`, `Флеш-накопитель USB 64 ГБ`,
`Сетевой коммутатор 24 порта`, `Документ-сканер`) остаются молчащими, а их top-1 в
альтернативах верный. Вывод: провал не в качестве поиска, а в формулировке («внешний
жёсткий диск» против «устройства запоминающие»), и лечится он не эмбеддером, а проверкой
гипотезы языковой моделью (эксп. 32).

**Практический вывод для эксплуатации.** Плотный режим включается без пересборки образа:
`EMBEDDER_BACKEND=tfidf` (или `VECTOR_SEARCH=true` при уже собранном артефакте под активный
эмбеддер). Для e5 артефакт нужно один раз собрать в образе:
`docker compose run --rm api python scripts/build_model.py --dense --gate` — до этого
честно работает лексика, и `/health/ready` так и говорит.

## Эксперимент 32. Третья ступень: LLM подтверждает top-3, а не классифицирует заново (2026-10-24)

**Задача.** Остаточная «яма» (эксп. 30, часть 4) — это строки, где перечень товар содержит,
top-1 верный, но групповая уверенность ниже порога (`pair_probability` 0.13–0.15). Словарь
здесь бессилен: разрыв в формулировке. Вопрос к языковой модели узкий: «какая из этих трёх
позиций — товар, или ни одна?».

**Устройство** (`api/app/services/llm_verifier.py`, по умолчанию **выключено**, подключено к
каталоговому режиму — тому, что работает по умолчанию):

* работает только для ответов `review`/`not_found`; `ok` не пересматривается;
* видит **не более трёх** позиций с кодами и может выбрать только одну из них или `none`;
* любой другой ответ (придуманный код, проза, битый JSON, таймаут, ошибка сети) игнорируется —
  ответ остаётся таким, каким его дал классификатор;
* подтверждённый код возвращается как `review` (кандидат для человека), **никогда** как `ok`;
* провенанс виден в новых необязательных полях контракта `verifier` (`llm-top3`) и
  `verifier_note`;
* кэш по паре «нормализованный запрос + тройка кодов» и потолок
  `LLM_VERIFIER_CALLS_PER_MINUTE` (60 по умолчанию) — выгрузка на 100 строк не может
  превратиться в неограниченный счёт;
* провайдер — любой OpenAI-совместимый endpoint (OpenAI, OpenRouter, vLLM, Ollama), ключ и
  модель задаются переменными окружения.

**Почему не «просто подключить LLM ко всему».** Три причины, все измеренные ранее: (1) LLM
дороже и медленнее лексики на порядок, а 70% строк решаются без него; (2) на строках вне
перечня модель языка охотно «находит» позицию — ограничение top-3 и запрет придумывать коды
превращают это в выбор из реальных вариантов; (3) без внешнего свидетельства нельзя отличить
подтверждение от правдоподобной выдумки, поэтому подтверждённый код остаётся `review`.
Отдельно: выдуманный код отклоняется тестом (`test_invented_code_never_reaches_the_response`).

**Что это даёт на числах.** Эффект не измерен на размеченном наборе намеренно: там нет
провайдера, а «прогнать LLM по офлайн-набору» нельзя. Ожидаемый эффект оценивается по
структуре остатка: из 63 молчаний двух выгрузок ~20 — товары, у которых перечень есть
(эксп. 30, часть 4). Это верхняя граница выигрыша ступени на этих файлах; нижняя — 0, если
модель отвечает `none`. Поэтому ступень выключена по умолчанию и включается владельцем
ключа, а не «сама собой улучшает» метрики.

## Эксперимент 33. Контур разметки: как из выгрузки с вердиктами получается обучение (2026-10-24)

**Задача.** Пользователь спросил, можно ли дообучить модель на файлах с правильными
ответами. Ответ: можно, но файл должен содержать **вердикты специалиста**, а не только
ответы модели.

**Почему нельзя на выгрузке как есть.** В обеих выгрузках (`classification-results (4).csv`,
`(5).csv`) колонки `user_verdict` и `corrected_code` пусты во всех 200 строках: это журнал
классификаций, а не разметка. Обучение на нём — обучение модели на собственных ответах:
порог и лексикон «подтвердят» себя, а измерять это будет нечем, потому что набор измерения
(`eval/labeled_examples.csv`) остался бы единственным честным источником.

**Что сделано** (`eval/feedback_loop.py`, 10 тестов):

| Вердикт в UI | Что попадает в файл меток |
| --- | --- |
| «Код верный» | `expected_okpd2` = код ответа, `label_kind=code` |
| «Код неверный» + правильный код | `expected_okpd2` = исправленный код, `label_kind=code` |
| «Нет в перечне» | пустой код, `label_kind=absent` |
| пусто / неизвестный вердикт / «неверный» без кода | строка пропускается и считается в отчёте |

Отчёт печатает то, что специалисту важнее процентов: сколько строк полосы `review`
оказались верными (это ширина «нашёл, но не уверен») и сколько **отвеченных** строк
оказались «нет в перечне» (это ложные коды, то есть сигнал, что лексикон/порог слишком
смелы). Файл меток пишется **отдельно** (`eval/labeled_from_feedback.csv`), набор измерения
не трогается; затем переобучение (`scripts/build_model.py --dense --gate`) и отдельный замер.

**Про «сгенерировать файлы для идеальной точности».** Такого файла не существует, и это не
вопрос объёма. Три ограничения, все измеренные:

1. **Неоднозначность ответа.** 81 семейство позиций повторяется в приложениях 2 и 3 под
   разными кодами («Мебель для офисов»: `31.01.1` и `31.01.11/31.01.12`). Оба кода верны;
   «идеальная точность» требует выбрать один — это решение о разметке, а не о данных.
2. **Закрытый перечень.** ~30 из 63 молчаний — товары, которых в перечне нет (ИБП,
   картридж, ручка, аптечка, огнетушитель). Любой файл, который «научит» отвечать на них,
   ухудшит главное свойство: не придумывать код.
3. **Синтетика не заменяет вердикт.** `eval/synthetic_eval.py` уже генерирует 659 запросов
   из каталога и словаря — они проверяют устойчивость формулировок, но не содержат нового
   знания: правильный ответ в них выведен из того же каталога. Обучение на такой генерации
   по кругу и даёт «переобучение на собственный словарь» (эксп. 9–11, `eval/learning-report.md`:
   ни один вариант не прошёл допуск).

Что реально двигает точность: (а) 300–500 строк с вердиктами специалиста по реальным
закупкам — их импортирует `eval/feedback_loop.py`; (б) заполнение спорных строк
(`docs/label-questions.md`, 41 строка в `unclear`) — это не «данные», а решения; (в) третья
ступень (эксп. 32) для остатка. **«Скачать модель»** при этом не нужно: e5 уже в образе
(`/opt/models/embedder`, первый `docker compose up --build` тянет ~10–15 минут), а
изменения кода применяются `docker compose up -d --build` без повторной загрузки весов;
переобучается только реранкер (секунды-минуты на CPU).

## Эксперимент 34. «Яма» пустых строк: почему модель молчит на реальной закупке и что это чинит (2026-10-25)

**Задача.** Пользователь прислал три новые выгрузки (300 строк реальных закупок: офисная
техника, склад, инженерка) и спросил, почему на фото половина строк — «Нет в перечне», хотя
уверенность в остальных выросла, и как это исправить.

**Диагноз по строкам, а не по среднему.** 115 из 300 строк были пустыми. Разбор:

В перечне 984 позиции, и офисного быта в нём нет почти целиком. Тишина здесь — **верное** поведение; те же товары помечены `absent` в `eval/labeled_examples.csv` |
| Позиция есть, топ-1 верный, но группа ниже порога | ~25 | `Счетчик электрической энергии трехфазный` → `26.51.63.130` (`pair_probability` 0.16), `Осциллограф цифровой запоминающий` → `26.51.42` (0.08), `Бульдозер колесный` → `28.92.21` (0.11) |
| Позиция есть, но топ-1 неверный | ~45 | `Прожектор …` уезжал в «Светодиоды», `Кабель силовой` — в «Кабели волоконно-оптические», `Портландцемент` — в «Мыло туалетное», `Кран шаровый` — в «Краны портальные» (грузоподъёмные) |

**Почему уверенность падает от спецификаторов.** Название позиции и строка закупки почти не
пересекаются словами: у закупщика `Осциллограф цифровой запоминающий`, у перечня
`Осциллоскопы и осциллографы электронно-лучевые`. Замер одного и того же кандидата:

| Запрос | `idf_coverage` | `known_coverage` | `pair_probability` |
| --- | ---: | ---: | ---: |
| `Осциллограф` | 1.00 | 1.00 | **0.485** |
| `Осциллограф цифровой запоминающий` | 0.55 | 0.33 | **0.084** |

Каждое незнакомое перечню слово реранкер читал как аргумент *против* совпадения: обучение
шло на коротких запросах вида «название», «бренд + голова», «голова + модификатор», а
технических спецификаторов в нём не было вовсе. Ранг был верным, ответ — «нет в перечне».

**Что сделано.**

1. **Волна 5 лексикона (19 мостов).** Только слова, которые *называют* товар:
   `портландцемент`, `прожектор`, `осциллограф`, `шприц`, `трансформатор`, `самосвал`,
   `полуприцеп`, `бульдозер`, `кабель`, `моноблок`, `генератор(ная)`, `шаровый`, `ламинатор`,
   `брошюровщик`, `счетчик`, `аккумулятор`, `клавиатура`, `папка`, `доска`. Омонимы закрыты
   `BRIDGE_REQUIRE`/`BRIDGE_VETO`: «кран шаровый» — арматура `28.14.13.131`, а не кран
   грузоподъёмный; «отвал бульдозера» — часть машины `28.92.28`, а не бульдозер; «кабель
   оптический» остаётся `27.31.1`; стартерный АКБ — `27.20.21`, стационарный — `27.20.22`;
   «генератор сигналов» — `27.90.40.150`, а не генераторная установка.
2. **Правило слабой подсказки** (`classifier._HEAD_RESCUE_FLOOR`, 21 тест). Если модель
   сказала «нет в перечне», но у лучшего кандидата есть код, его `pair_probability` ≥ 0.08 и
   **головное слово строки** написано в названии позиции — ответ становится `review`
   («нашёл, но не уверен»), а не пустой строкой. Голова — первое слово-товар: модификаторы
   области («офисный», «промышленный») и вариантные прилагательные пропускаются, поэтому
   `Сейф офисный` не якорится в «Машины офисные прочие», а `Щётка для обуви` — в «Обувь».
   `ok` это правило не выдаёт никогда, и код без позиции тоже: инвариант 5 в силе.
   Правило живёт в общем помощнике `_head_rescued_answer` и подключено в обоих бэкендах —
   каталожном и Qdrant, иначе прод с векторным поиском отвечал бы «нет в перечне» там, где
   каталожный режим уже показывает `review` (`api/tests/test_qdrant_dedup.py`).
3. **Порог `ok` 0.77 → 0.80.** Пересборка на новых парах дала шесть неверных уверенных
   ответов из 180 против четырёх из 178 в записанной базе. На 0.80 их 5 из 182 (97.3 %):
   строки, которые порог снимает с `ok`, остаются видимыми как `review`, число пустых ответов
   от него не зависит.

быть пустой).

**Проверяемость: почему отгружен другой файл, чем в промежуточном замере.** Первый вариант
сборки (sha `8bf553f5…`) давал 190/201 и ECE 0.026, и его хотелось оставить: цифры лучше. Но
CI-шаг «Shipped artifacts match a rebuild» переобучает базу тем же кодом и сверяет описание
прогона — и поймал расхождение: 31602 пары против 31646 у отгруженного файла. Причина
конкретная: мост «генераторная» попал в лексикон **после** той сборки, поэтому артефакт был
обучен на одном наборе признаков, а служился с другим (проверено: снимаем `"генераторная"` из
`BRIDGES` — пересборка снова даёт 31646 пар и те же веса). Отгружен воспроизводимый файл
(`a50fd4aa…`, две независимые сборки байт в байт): top-1 191/201, ECE 0.037. То есть «хорошая»
калибровка 0.026 была свойством рассогласованной пары «старый артефакт + новая лексика», а не
качества модели; 0.037 — свойство отгруженной пары и остаётся в 4 раза лучше цели 0.15.

**Честно о цене.** Половина новых `review` — верные (`Кран-балка` → `28.22.14.121`,
`Трансформатор` → `27.11.4`, `Самосвал` → `28.92.29`, `Сварочный аппарат` → `27.90.31.110`),
половина — соседние позиции или мусор (`Шкаф распределительный` → «Шкафы холодильные»,
`Паста теплопроводная` → «Пасты масляные», `Алюминий первичный` → «Конструкции из алюминия»).
Это и есть смысл статуса «нашёл, но не уверен»: специалист проверяет одну строку вместо того,
чтобы искать позицию с нуля. Строки, где перечня нет, остаются пустыми — и это главное
свойство, которое мы не стали менять в угоду «чтобы всё находилось».

**Что осталось.** ~45 из 68 пустых строк — товары вне перечня (верное поведение). Внутри них
`ИБП`, `Маршрутизатор`, `Реле`, `Датчик температуры`, `Манометр`, `Расходомер` — вопросы
к разметке (`docs/label-questions.md`), а не к модели: перечень либо не содержит такой
позиции, либо относит её к общей группе (`27.12.2` «Устройства коммутации или защиты…»).
Открытая техническая задача — реранкер по-прежнему не видит технических спецификаторов в
обучении: попытка добавить их в `make_query_variants` (`SPEC_WORDS`) дала −2 top-1 на
наборе разметки при +7 ответах на реальных строках, то есть была отвергнута и не отгружена.

## Эксперимент 35. Волна 6: что осталось пустым после волны 5 и почему (2026-10-25)

**Задача.** После волны 5 (эксп. 34) на трёх выгрузках по 100 строк оставалось 68 пустых
строк из 300. Пользователь повторил прогон на отгруженной сборке — числа совпали с замером
((6) 49/15/36, (7) 76/17/7, (8) 47/28/25), то есть вопрос был не в среде, а в покрытии.
Плюс два технических долга из эксп. 34: «реранкер не видит спецификаторов» и «калибровка
просела до 0.037».

**Разбор 68 строк по причинам.** Каждая строка разобрана вручную, не по среднему:

| Класс | Строк | Примеры | Что значит |
| --- | ---: | --- | --- |

| Товар в перечне есть, но моста нет | 15 | манометр, расходомер, реле, маршрутизатор, мультиметр, сервер, рукав, патч-корд, флеш-накопитель, системный блок, фильтр, стеклоткань | **чинится лексиконом** |

**Волна 6 лексикона (13 мостов).** Только слова, которые *называют* товар, и только туда, где
позиция в `data/data.csv` действительно есть — каждое слово-цель проверено по каталогу
(`test_every_bridge_target_is_a_catalog_word_with_a_canonical_code`):

| Слово специалиста | Слово перечня | Позиция |
| --- | --- | --- |
| манометр | давления | `26.51.52.130` Приборы для измерения или контроля давления |

Три решения стоят отдельного объяснения, потому что это не словарные, а продуктовые:

* **«реле» ведёт на «цепей», а не на «коммутации».** На «коммутации» уже висит коммутатор с
  каноническим кодом `26.30.11.110` (средства связи); одна цель моста не может указывать на две
  разные позиции, а реле — это `27.12.2`.
* **«фильтр» срабатывает только вместе со словом о жидкости** (`BRIDGE_REQUIRE`). Без стража
  медицинский «фильтр дыхательный» (`32.50.50`) уезжал в оборудование для очистки жидкостей.
* **«системный» — голова строки, поэтому мост висит на ней, а не на «блоке»**: «блок питания» и
  «блок бесперебойного питания» — не системный блок.

**Стеклоткань: одна строка, которую волна сначала сломала.** После пересборки с волной 6
«Ткань из стекловолокна» стала отвечать общей позицией `13.2` вместо собственной `13.20.46`
(веса сместились). Разбор показал, что моста на это слово не было вовсе: добавили
`стекловолокно/стеклоткань → стекловолокна` с каноническим кодом, и строка вернулась. Это
иллюстрация правила: **волна без пересборки и перезамера — не сделана**.

**Два отвергнутых подхода (измерены, не отгружены).**

1. *Снятие спецификаторов на выдаче.* Гипотеза: собрать второй вариант запроса без
   прилагательных-атрибутов и брать более уверенный ответ. Замер на 347 строках стресс-набора
   (`eval/specifier_stress.py`): 312 → 314 верных (+2 из 347, +0.6 %), при этом «Радиаторы
   чугунные» перестают отличаться от «Радиаторов стальных» (`25.21.11.110` против `.120`) —
   слово «чугунный» здесь несёт идентичность. Отвергнуто: плата за 2 строки — целый класс
   ошибок. `ml/specifiers.py` остался как словарь и как инструмент замера.
2. *Обучение на строках со спецификаторами.* Гипотеза: научить модель, что незнакомое слово —
   не аргумент против совпадения, добавив спецификаторы в синтетические варианты запросов
   (`SPEC_WORDS` в `make_query_variants`). Сборка выросла с 32 тыс. до 39 тыс. пар. Результат —
   ровно ничего там, где ожидался эффект: `short+attr` 78.2 % → 78.2 %, `name+attr` 96.0 → 96.6 %,
   `short` 83.2 → 82.4 %, а на реальных строках тишина выросла 56 → 58. ECE при этом улучшился
   (0.0272 → 0.0209), но это не то, что чинилось. Отвергнуто: цена — две пустые строки на 300.
   Долг «модель не видит спецификаторов» закрыт как **решение**, а не как исправление: два
   измеренных подхода проиграли, а правило слабой подсказки (эксп. 34) закрывает те же строки
   без переобучения.

**Третий отвергнутый вариант: «кодовая пара» для обобщающей строки.** Восемь пустых строк — это
каталоговая семья «Контейнеры для заготовки, хранения и транспортирования донорской крови»:
обобщающая строка приложения 4 не имеет кода ОКПД2 («Не указан»), поэтому инвариант 5 запрещает
её как ответ, а её же кодовые дети стоят следующими в ранге. Правило «если лидер без кода, взять
кодового соседа с тем же названием» реализовано, измерено и **не сработало**: названия
отличаются одним словом («транспортирования» против «транспортировки»), точного совпадения нет,
а похожесть по стемам даёт 0.55 — порог, при котором правило начнёт склеивать разные позиции.
Кода в коде нет; случай описан здесь, чтобы его не пытались «починить» ещё раз.

**Стресс-набор как инструмент.** Чтобы такие решения принимались замером, а не вкусом, добавлен
`eval/specifier_stress.py`: из каталога детерминированно (seed 1875) строятся три базы — точное
название позиции, первые 3-4 слова названия и продуктовое слово моста — каждая сама по себе и с
1-3 техническими атрибутами (`SPEC_EXAMPLES`). Истина — множество кодов позиции (87 названий из
746 повторяются в приложениях с разными кодами). Записанный замер — `eval/baselines/specifier_stress.json`,
его проверяет `api/tests/test_specifier_stress.py`: падение больше 0.5 п.п. — красный тест.

| Форма | Строк | top-1 | top-3 | тишина | молчит, но ранг 1 верный |
| --- | ---: | ---: | ---: | ---: | ---: |
| `name` (точное название) | 149 | 97.3 % | 100 % | 0.0 % | 0.0 % |
| `name+attr` | 149 | 96.0 % | 100 % | 0.0 % | 0.0 % |
| `short` (как пишет специалист) | 119 | 83.2 % | 98.3 % | 1.7 % | 1.7 % |
| `short+attr` | 119 | 78.2 % | 98.3 % | 5.0 % | **5.0 %** |
| `bridge` (продуктовое слово) | 86 | 97.7 % | 100 % | 0.0 % | 0.0 % |
| `bridge+attr` | 86 | 96.5 % | 100 % | 0.0 % | 0.0 % |

Две вещи видны сразу и обе важны. Первая: атрибуты стоят 1.3 п.п. на точном названии и 5 п.п.

Вторая: **вся оставшаяся тишина на `short+attr` — это «молчит, но ранг 1 верный»** (6 из 6),

### Калибровка: ECE 0.019 → 0.012, и это не «стало лучше»

Волна сначала дала **ECE 0.0363** при неизменном top-1 — то есть гейт краснел на метрике, которая
к качеству ответов отношения не имеет. Разбор:

* Сырая ECE новой сборки — **0.012**, показная после Platt-карты — 0.036. Карта **ухудшала**
  шкалу: площадка насыщена (688 отвеченных строк, средняя сырая уверенность 0.969 при точности
  0.958), поэтому подбор интерсепта — это разность двух чисел у самого верха шкалы.
* Построены четыре сборки одного и того же кода с разными сидами: ECE 0.0176 / 0.0219 / 0.0254 /
  0.0363, top-1 везде 191/201. Отличались только интерсепты карты: −0.341 / +0.155 / +0.277 /
  +0.368 — при ошибке площадки ≈0.2, то есть **знак поправки выбирал сид**, а не данные.
* Правило (и доктрина): карта показывается, только если её сдвиг больше собственной ошибки —
  `CALIBRATION_SHIFT_SIGMAS = 1.96`, ошибка из информации Фишера логистической подгонки
  (`sum(p(1-p))`), сдвиг — `(a-1)*logit(p_тип) + b`. Для этой сборки 0.341 / 0.199 = **1.7 σ** —
  внутри полосы, карта не надевается, отгружается сырая шкала. Доказательство решения пишется в
  артефакт (`meta.calibration_platform`: `candidate_intercept`, `shift`, `shift_se`,
  `identity_kept`), и `test_artifact_has_a_monotone_calibration` проверяет именно его, а не
  «карта обязана быть неединичной».
* Цена решения: если модель действительно переуверена, ECE на площадке это покажет, и карта
  вернётся — но только когда сдвиг переживёт ошибку. Выгода: ECE перестал быть лотереей сида
  (0.012 против 0.018…0.036), а `confidence` совпадает с `confidence_raw`.

Открытый долг из этого: `ml/artifacts/reranker.tfidf.json` построен 2026-10-24 по старому правилу,
поэтому его ECE (0.029) больше не сравним с лексическим (0.012) — строковые метрики сравнимы,
шкала нет (`docs/next-steps.md`).

**Про точность `ok`, без округления в свою пользу.** В записи прежнего файла стояло 177/182
(5 неверных), у нового — 180/187 (7 неверных). Две строки разницы — это цена трёх верных
переходов в `ok`: «Свитер» тоже перешёл и остался неверным. Пул четырёх прогонов, на котором
принимает решение гейт, даёт 25 неверных `ok` против 25, то есть на согласованной конфигурации
разницы нет; одиночный замер гуляет на две строки и записываться как «стало лучше» не должен.
Строка базовой линии обновлена явно (`eval/baselines/dense-tfidf.json`, 193/201, ECE 0.0311),
и это единственный замер, относительно которого теперь сравнивается CI.

**Про отчёт гейта.** Прогон писался до того, как в отчёт добавили `baseline.meta` (описание
прогона базового артефакта — то, что не зависит от сборки BLAS). Поле добавлено к отчёту
механически: файл базовой линии воспроизводится байт в байт (sha256 `563da4a2…` в отчёте
совпадает с независимой пересборкой), и описание выведено из этого файла, а не переписано
руками. Следующие отчёты пишут его сразу.

**Вывод.** Расширять допуск ECE не нужно и переобучать «под допуск» тоже: долг был не в
признаках, а в артефакте, собранном до правила значимости. Гейт и раньше сравнивал объединённые
таблицы надёжности, а не два одиночных ECE; теперь то же правило применено к отгруженному файлу,
и новый отчёт гейта хранит описание базового прогона (`baseline.meta`), чтобы происхождение
проверялось на любой машине, а не по хешу, зависящему от сборки BLAS.

## Эксперимент 38. ML-4 читал не те схемы: три способа потерять 300 вердиктов (2026-10-25)

**Задача.** Пункт ML-4 («вердикты специалиста → hard negatives») стоял как «механизм готов,
ждёт данных». Проверка на реальных форматах показала, что данных он бы не дождался: он их не
узнаёт.

**Три схемы.** Продукт пишет вердикты в двух местах, и обе схемы отличались от той, на которой
механизм тестировался:

| Источник | Колонки |
| --- | --- |
| выгрузка интерфейса (`frontend/src/files.ts`) | `query;code;title;status;…;user_verdict;corrected_code;verifier;verifier_note;row` |
| журнал обратной связи (`feedback_store.py`) | `query;predicted_code;verdict;corrected_code` (Postgres или SQLite `classification_feedback`) |
| фикстуры модуля | `query;proposed_code;verdict;correct_code;comment` |

`ml/hard_negatives.load_feedback` знал только третью. Воспроизведение на трёх строках выгрузки
интерфейса: `usable: []`, пар 0. На схеме журнала «не в перечне» записан как `absent` — такого
вердикта в списке не было, строка отбрасывалась молча. Хуже третье: вердикт `incorrect` с
`corrected_code` давал **9 пар и 0 позитивов** — весь шорт-лист помечался негативным, потому что
исправленный код читался из несуществующей колонки `correct_code`. То есть первые же 300
вердиктов обучили бы модель обратному.

**Что сделано.** Колонки читаются по псевдонимам (`predicted_code`/`proposed_code`/`code`,
`user_verdict`/`verdict`, `corrected_code`/`correct_code`, `verifier_note`/`comment`); вердикты
сравниваются без учёта регистра и разделителей (`not_in_list` ≡ `not in list`) и знают
`absent`/«нет в перечне»; добавлен `load_feedback` по суффиксу `.sqlite` (та же таблица, что
пишет API). Появился `MiningReport`: сколько вердиктов, сколько полезных, сколько пар, сколько
«неверно» осталось без пригодного кода, и почему пар нет, словами самого файла. Вердикт
`incorrect` без исправленного кода или с кодом вне каталога **пропускается**, а не превращается
в all-negative; это и есть защита от отравления. CLI получил `--min-pairs 300` (код возврата 1,
если DoD не выполнен).

**Проверка.** Выгрузка интерфейса (3 строки: `incorrect`, `absent`, `correct`) → 20 пар
(1 позитив, 19 hard negatives, один из них — ответ модели, которого уже нет в коротком списке).
SQLite-журнал (2 строки) → 19 пар. Журнал без вердиктов → 0 пар и диагноз «это журнал
классификаций, а не разметка». Тестов стало 18 вместо 7: обе реальные схемы, SQLite, ядро
защиты от all-negative, диагностика, повторы и противоречия.

**Один запрос — один вердикт.** Выгрузка — это журнал, а не таблица: один и тот же запрос
приходит повторно после переэкспорта, а два проверяющих могут дать разные вердикты (`incorrect`
с исправлением и `absent`). Обучение на обеих строках пометило бы одну и ту же позицию
и позитивом, и негативом. Поэтому вердикты сворачиваются по запросу с приоритетом «неверно»
(в нём есть позиция, которую модель должна была поставить первой), а сам факт противоречия
печатается в отчёте. Проверено в обе стороны: порядок строк в файле на выбор не влияет.

**Ответ модели — негатив, даже если он выпал из короткого списка.** Ретрив между ответом и
вердиктом может уехать, и подтверждённо неверный код переставал быть негативом. Теперь позиция,
которую специалист назвал неверной, добавляется в пары явно (`label=0`, нулевые признаки) —
вердикт человека не теряется из-за дрейфа поиска.

**Что осталось.** Сам DoD «≥300 пар из реального трафика» — это данные, а не код: нужны
накопленные вердикты (`POST /feedback`) или выгрузка с заполненным `user_verdict`. Команда
проверки готова: `python -m ml.hard_negatives "выгрузка.csv" --min-pairs 300`.

## Эксперимент 39. ML-7 закрыт: разбиение длинного названия улучшает ранжирование и портит статус (2026-10-25)

**Задача.** `LONG_TITLE_SPLIT=1` (голова + квалификаторы, вес квалификатора 0.3) был измерен в
эксп. 36 как размен: +2.2 п.п. top-1 на срезе длинных названий и +10 уверенно неверных кодов.
Решение «включать или нет» висело на продукте. Здесь проверены две вещи, которые могли этот
размен отменить: (1) не был ли замер артефактом несовпадения обучения и сервинга (переключатель
включали на файле, обученном без него) и (2) что именно улучшает разбиение — ранжирование или
уверенность.

**Матрица 2×2** (лексический артефакт, 139 длинных позиций, запрос — первые 8 слов головы;
колонки — `top-1 / review / неверный код / тишина`):

| Обучение | Сервинг | Результат |
| --- | --- | --- |
| без разбиения | без разбиения | 35 / 35 / **17** / 52 |
| без разбиения | с разбиением | 38 / 22 / **27** / 52 |
| с разбиением | с разбиением | 38 / 22 / **27** / 52 |
| с разбиением | без разбиения | 35 / 38 / **14** / 52 |

Обучение с разбиением **не меняет ничего**: строка «с/с» совпадает со строкой «без/с» построчно.
Гипотеза «артефакт калибровался без разбиения, поэтому уверенность и поехала» отвергнута —
пороги уверенности при обучении с разбиением сдвигаются на 0.003 (0.686 → 0.683), а не на
величину эффекта.

**Ранжирование отдельно от статуса.** Если отключить пороги (`CATALOG_OK_FLOOR=0.01`,
`CATALOG_REVIEW_FLOOR=0`) и мерить только первого кандидата, разбиение даёт **+3 строки**:
rank-1 36 → 39, rank-3 127 → 128, и этот выигрыш одинаков для обоих артефактов. То есть
улучшение ранжирования реально; но статусная машина превращает его в 3 верных `ok` и 10
неверных.

**На плотном пути размен мягче** (отгруженный `reranker.tfidf.json`, порог `ok=0.80`):
без разбиения 30 / 43 / 14 / 52, с разбиением 33 / 38 / **16** / 52 — +3 top-1, +2 неверных
кода, −5 подсказок `review`. Причина: плотный артефакт вообще осторожнее на этом срезе
(43 подсказки против 35), поэтому и «перерешительность» от разбиения меньше.

**Вывод.** Переключатель остаётся выключенным, и это больше не продуктовый вопрос: при
одинаковом обучении и сервинге разбиение не даёт ни одной лишней верной подсказки, а неверных
уверенных кодов добавляет (10 на лексике, 2 на плотном пути). Если когда-нибудь включать — то
только вместе с правкой на стороне уверенности: признаки `candidate_precision`/`idf_precision`
с весом квалификатора 0.3 поднимают и правильные, и неправильные длинные кандидаты, а
confidence-модель читает их через `pair_probability`. Это отдельная задача, а не переключатель.
