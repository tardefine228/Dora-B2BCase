# Задача B: итоговый отчёт по закупке — результат

Дата: 11.11.2026. Ветка: `arena/12f6d33c-dora-b2bcase`.

## Что видит специалист

После загрузки списка на странице появляются три карточки: «Принято», «Требуют
проверки», «Не найдено», с числом и долей позиций. Карточка фильтрует таблицу.
Отдельно видно, сколько принято моделью и сколько выбрано специалистом. Фильтр
причин и сортировка «Сначала рискованные» работают по серверным полям; кнопка
перехода ведёт к первой проблемной строке. Причина и необходимое действие выводятся
прямо в строке, а не только внутри раскрывающейся карточки.

XLSX содержит «Результаты», «Сводка» и отсортированные по риску «Требуют проверки».
CSV и основной лист XLSX содержат bucket, risk rank, машинный код и текст причин,
исходный номер строки и provenance уточнения. Экспортируется текущий отфильтрованный/
отсортированный экран; сводка в XLSX относится ко всей закупке.

## Единая decision table

Источник истины — `api/app/services/procurement_report.py`. Batch response содержит
`report.summary` и `report.items`; UI и экспорт не вычисляют собственные юридические
бuckets.

| Условие строки | Bucket | Причина / rank |
| --- | --- | --- |
| `not_found` | `not_found` | `not_found`, 60 |
| Активное `needs_clarification` | `needs_review` | `ambiguous_name`, 90 |
| Несколько кодов | `needs_review` | `multiple_codes`, 100 |
| Исключение/неподтверждённая роль | `needs_review` | `code_exception`, 95 |
| `catalog_review_required=true` | `needs_review` | `catalog_review_required`, 85 |
| Обычный model `review` | `needs_review` | `low_confidence`, 70 |
| Код отсутствует | `needs_review` | `code_missing`, 80 |
| `ok` без блокирующих причин | `accepted` | 0 |

Инварианты:

```text
accepted + needs_review + not_found = total
accepted = auto_accepted + specialist_resolved
```

`total` в summary — уже обработанные строки, поэтому инвариант выполняется и во время
batch progress. Причины независимы и их счётчики могут пересекаться. Выбор специалиста,
который остаётся `review` из-за исключения/сверки, не попадает в accepted. После resolve
строка сначала атомарно сохраняется, а следующий GET заново вычисляет report.

## Возврат к отчёту и privacy

`GET /classify/batch/{job_id}` остаётся источником истины до истечения `JOB_TTL_HOURS`
(по умолчанию 24 часа). В localStorage сохраняются только `{id,total,filename}`; названия
товаров и коды там не записываются. Session snapshot по-прежнему служит только для Back.
После reload или закрытия/открытия страницы UI повторно запрашивает серверный report.
SQLite/PostgreSQL позволяют пережить рестарт API/worker; Memory store такой гарантии не даёт.

Неизвестный/истёкший ID получает 404 и явное сообщение; устаревший session snapshot его
не подменяет. При сетевой ошибке marker сохраняется для повторной попытки. «Закрыть отчёт»
удаляет локальный marker и очищает экран, не изменяя серверный TTL. Глобальной истории
и новых аккаунтов нет.
