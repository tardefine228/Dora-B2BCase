# Задача A: уточнение неоднозначных запросов — результат

Дата: 11.11.2026. Ветка: `arena/12f6d33c-dora-b2bcase`.

## Что изменилось для специалиста

Общее название больше не превращается в окончательный код только потому, что одна
из позиций получила высокий model score. Для `needs_clarification` UI показывает
вопрос и кнопки вариантов, а `code/title` остаются пустыми. Выбор выполняется одним
нажатием и в одиночном поиске, и в каждой строке пакета. После сохранения видно
«Выбрано специалистом», а не «модель уверена». Оценка модели не показывается как
уверенность человека.

Пример: «автомобиль» → легковой, грузовой, пожарный, скорой помощи, самосвал и
специальные транспортные средства. «Легковой автомобиль» остаётся обычным запросом.
Прямой ОКПД2 также не вызывает вопрос и получает `decision_source=direct_code`.

## Decision table

| Условие | Решение | Комментарий |
| --- | --- | --- |
| Экспертно зарегистрированное общее слово без уточняющего признака | `needs_clarification` | Автомобиль, мебель, светильник, кран, компьютер, счётчик, фильтр, насос |
| То же слово + тип/назначение | обычная классификация | Например, шаровый кран, счётчик электроэнергии |
| Запрошенное название совпадает с названием, которому в каталоге назначено несколько кодов | `needs_clarification` | Случайный слабый top-1 с таким названием вопрос не создаёт |
| Одиночное товарное слово и несколько лексически связанных кандидатов | data-driven fallback | Кандидат должен начинаться с того же товарного слова; производные товары не считаются |
| Каноническая родовая позиция из доктрины | обычный ответ | «Обувь» → 15.2, «Одежда» → 14.1; реестр выше — явное исключение, а не общее правило |
| Явный ОКПД2 | обычный ответ, `direct_code` | Код сам является уточнением |
| Выбранная строка — исключение или требует сверки | `review` после выбора | Не становится `ok` только потому, что её выбрал человек |
| Обычная включённая строка после выбора | `ok`, `specialist` | Исходный ответ модели сохраняется в `resolution.original` |

Guard находится в `api/app/services/ambiguity.py` и применяется после LLM и
shortlist в Catalog и Qdrant. Повторы «код + название» удаляются; одинаковый код с
разными юридическими названиями не склеивается. Опция ссылается на `record_id` и
`clause_url`.

## Контракт 2.0

Новые поля и инварианты подробно описаны в `docs/api-contract.md`.

* `needs_clarification`: `code/title=null`, `confidence=0`, `alternatives=[]`,
  `clarification.options` содержит минимум две опции.
* `clarification.original` хранит код, название, статус, confidence и alternatives
  исходной модели. Метрики retrieval/calibration используют именно его, а не пустой
  ответ guard.
* `option_id` выдаёт сервер. Клиент не может подставить произвольный код.
* `catalog_sha256` связывает вопрос и ответ. Другая версия каталога → 409.
* `decision_source`: `model`, `specialist`, `direct_code`.
* `item_id` сохраняет серверный индекс строки при сортировки таблицы.
* `attention_reasons` объясняет неоднозначность/дубли/исключение/сверку.

Resolver'ы:

```text
POST /classify/resolve
POST /classify/batch/{job_id}/items/{item_id}/resolve
```

Batch-выбор атомарно сохраняется в Memory, SQLite и PostgreSQL. Повторный и
конкурентный resolve не перезаписывает уже сохранённое решение. Новая миграция не
нужна: результат остаётся JSON в существующей записи job. Серверный CSV, клиентские
CSV и XLSX содержат вопрос, опции, источник решения и исходный код модели.

## Регрессионный набор

`eval/ambiguity_examples.csv`: 25 сценариев — 9 `clarify`, 16 `code`.
Положительные примеры проверяют не только статус, но и обязательные `record_id`
опций. Негативные контроли включают конкретные модификаторы, прямой код, ноутбук,
бумагу и канонические родовые позиции. Runner: `eval/run_ambiguity_eval.py`; он
включён в `.github/workflows/lint.yml` для lexical и TF‑IDF.

Фактические прогоны 11.11.2026:

| Конфигурация | Всего | Clarification recall | Unambiguous pass | Навязанных кодов |
| --- | ---: | ---: | ---: | ---: |
| lexical / vector off | 25/25 | 100 % | 100 % | 0 |
| TF‑IDF / memory | 25/25 | 100 % | 100 % | 0 |

Это небольшой экспертный набор, а не гарантия recall на любом реальном запросе.
Расширение реестра требует новых положительных и негативных строк.

Общий `eval/run_eval.py` учитывает новый статус без смешивания шкал: прямой top-1
остаётся отдельной метрикой, а `needs_clarification` засчитывается как верное решение
только при наличии ожидаемого кода среди минимум двух опций. Вопрос без нужного кода —
ошибка. Вопросы исключены из ECE, поскольку их нулевая confidence не является оценкой
модели. Baselines не обновлялись: после корректного учёта обе конфигурации прошли прежний
row-by-row gate.

## Что не проверено в этой среде

* **E5:** sentence-transformers и веса не установлены; скачивание модели недоступно
  из-за сетевых ограничений sandbox. TF‑IDF не выдаётся за E5.
* **Docker Compose:** Docker CLI отсутствует. Production frontend build и живой
  Uvicorn проверены отдельно, но это не заменяет clean `docker compose up --build`.
* **Живой PostgreSQL:** в sandbox нет сервера. SQLite/API и полный существующий
  PostgreSQL test-suite пройдены там, где среда предоставляет fixtures; атомарная
  реализация Postgres использует `SELECT … FOR UPDATE`, но требует проверки на
  целевом стеке.
