# План работ по дополнительным задачам организаторов A и B

> Это исходный архитектурный план. Фактические объём, decision tables и проверки:
> `docs/ambiguity-clarification-result-2026-11-11.md` и
> `docs/procurement-report-result-2026-11-11.md`. Не реализованные экспертные расширения
> (аудит всех 87 дублей, разметка 400 реальных запросов, версионная история изменения
> уточнения) не выдаются за выполненные.

Дата анализа: 11.11.2026  
Источник требований: `07_Дополнительные_задачи_Задача_2_Dora_B2BCase.pdf`, 2 страницы.  
Обязательные ограничения сохраняются: прежний стек и запуск `docker compose up --build`.

## 1. Стратегическое решение

**Основная номинация — «самое верное решение». Технологичность — усилитель, а не отдельная гонка за стеком.**

Причины:

1. В проекте уже есть сильная техническая основа: FastAPI, React, PostgreSQL, Celery/Redis,
   Qdrant, E5/TF-IDF, обученный реранкер, калибровка, источники ПП, feedback, миграции,
   observability, CI и Docker smoke. Ещё один эмбеддер или LLM почти не добавит ценности
   по новым задачам.
2. Организаторы указали на концептуальную ошибку: система уверенно выбирает код там,
   где у неё нет оснований предпочесть одну позицию другой. Это исправляется не усложнением
   модели, а правильной моделью решения: **ответ / уточнение / ручная проверка / не найдено**.
3. Текущие метрики не измеряют эту ошибку. Запросу без единственно верного ответа всё равно
   навязывается top-1. Значит, главный выигрыш — новая разметка, запрет уверенного ответа
   на неоднозначности и сквозной человеко-машинный сценарий.
4. Задача B позволяет доказать верность на уровне всей закупки, а не только top-1:
   система обязана сохранять причины риска, выбор специалиста и исходный результат.

Формулировка для защиты:

> Мы не пытаемся угадать код любой ценой. Сервис отличает уникальное совпадение от равнозначных
> толкований, не выдаёт произвольный top-1 за ответ, позволяет специалисту уточнить товар одним
> действием и сохраняет проверяемый отчёт по всей закупке.

## 2. Что уже есть и что именно не закрыто

### 2.1. Сильная база, которую надо переиспользовать

- Гибридный catalog backend: лексический поиск + векторы + реранкер + калиброванные пороги.
- Пакетная обработка до 100 позиций, SSE/polling, PostgreSQL/SQLite job store.
- Таблица результатов, альтернативы, ссылки на нормативный источник, условия по приложениям,
  Excel/CSV export и вердикты специалиста.
- Проверенная приёмка 26.10.2026 на полном стеке: 18/20 строгих ответов, 100 позиций за 7,59 с,
  обновление каталога без передеплоя. Это исторический результат приёмки, перед сдачей его нужно
  переснять после изменений.
- Качественные инженерные практики: контрактные тесты, quality gate, миграции, backup/restore,
  Playwright + axe, мониторинг, явный запрет тихой деградации модели.

### 2.2. Задача A сейчас не реализована

В контракте только `ok / review / not_found`. Нет состояния «нужно уточнение», машинной причины
неоднозначности, управляемых вариантов уточнения и однокликового разрешения. Альтернативы —
информационный список максимум из трёх позиций, а не механизм выбора.

Фактический probe текущего кода 11.11.2026, воспроизводимая конфигурация
`EMBEDDER_BACKEND=tfidf`, `VECTOR_STORE=memory`, отгруженный `reranker.tfidf.json`:

| Запрос | Текущий ответ | Почему это подтверждает проблему |
| --- | --- | --- |
| `автомобиль` | `ok`, **29.10.59.140 «Автомобили пожарные»**, 81,75% | Это ровно опасный сценарий из PDF; легковой и скорая — только альтернативы |
| `мебель` | `ok`, **31.02.10 «Мебель кухонная»**, 87,67% | Общее слово произвольно сужено до кухни |
| `светильник` | `ok`, **27.40.22**, настольные/прикроватные/напольные, 97,19% | Высокий процент создаёт ложное ощущение однозначности |
| `кран` | `review`, краны портальные | Даже `review` оставляет произвольный top-1 вместо вопроса о типе крана |
| `компьютер` | `review`, томографы компьютерные | Нужны не только пороги, но и контроль смысловых веток кандидатов |

Контрольные запросы `автомобиль легковой` и `автомобиль грузовой` дают ожидаемые разные коды.
Их нельзя сломать новым guard. Запрос `игрушки`, наоборот, имеет явную родовую позицию «Игры и
игрушки» и не должен автоматически становиться неоднозначным.

Числа зависят от эмбеддера; перед релизом те же кейсы обязательно прогоняются на полном E5.
Но отсутствие слоя неоднозначности является архитектурным фактом независимо от эмбеддера.

### 2.3. Задача B реализована только частично

Уже есть таблица, статусы, условия закупки, экспорт и серверное хранение batch-результатов.
Не хватает:

- сводки по закупке и взаимно однозначных правил подсчёта;
- типизированных причин ручной проверки;
- фильтров и сортировки по риску;
- отчёта со сводкой и причинами в экспорте;
- восстановления **завершённого** отчёта после reload/закрытия страницы;
- сохранения выбора уточнения внутри batch-результата.

Важный текущий конфликт: `frontend/src/view.ts` и `App.tsx` намеренно удаляют просмотр при reload,
а `resumeActiveJob()` удаляет marker завершённой задачи и просит загрузить файл повторно. На сервере
job при этом ещё может существовать, но UI теряет к нему доступ. `JOB_TTL_HOURS=24` также не стоит
молча выдавать за долговременное хранение отчёта.

### 2.4. Дополнительные ограничения для номинации «самое верное»

- 400 реальных запросов есть, но экспертных вердиктов по ним нет; `real_queries.csv` специально не
  сфабрикован. Поэтому независимую точность на реальном трафике пока заявлять нельзя.
- 41 `unclear` ждёт предметного решения; редакция ПП №1875 на дату закупки не сверена полностью.
- В каталоге 87 нормализованных по названию групп с более чем одним текстовым кодом. Среди них есть
  как настоящие разные коды, так и возможные форматные варианты (`28.3`/`28.30`,
  `27.20.21`/`27.20.21.000`). Нужна экспертная классификация, а не автоматическое объявление всех
  дублей ошибкой или эквивалентностью.
- Текущая eval-метрика допускает prefix-совпадение кодов, а exact-name regression засчитывает тот же
  title даже при другом коде. Для новых проверок нужна отдельная **строгая** метрика кода и позиции,
  иначе многокодовые дубли будут скрыты.
- `code_role="Исключение"` и `catalog_review_required` сейчас информационные и не меняют статус.
  Для итогового отчёта такие строки нельзя считать автоматически принятыми без продуктового правила.

## 3. Целевая модель решения

### 3.1. Четыре разных состояния, а не три

| Состояние | Код до действия человека | Смысл |
| --- | --- | --- |
| `ok` | есть | Одно обоснованное толкование, нет блокирующих risk flags |
| `needs_clarification` | **нет** | Есть минимум два равнозначных толкования; нужен выбор специалиста |
| `review` | код-кандидат есть | Есть ведущая позиция, но её нужно проверить по указанной причине |
| `not_found` | нет | Надёжного совпадения нет; это не юридическое доказательство отсутствия товара |

Нельзя кодировать неоднозначность как `not_found`: товар как раз найден, но имеет несколько смыслов.
Нельзя оставлять её как `ok` или обычный `review`: интерфейс продолжит показывать произвольный код.

Поскольку меняется enum и часть инвариантов, синхронно обновляем API, frontend, экспорт и тесты и
повышаем `contract_version` до **2.0**. Незаметно вставлять новое состояние в v1 нельзя.

Дополнительные поля результата:

- `attention_reasons[]`: стабильные машинные коды + локализуемое объяснение;
- `clarification`: вопрос и минимум две опции с `option_id`, title, code, clause и source;
- `decision_source`: `model / specialist / direct_code`;
- `catalog_sha256`: версия данных, на которых построены опции;
- `item_id`: стабильный идентификатор строки batch, не `name + code` и не индекс после сортировки;
- `resolution`: выбранная опция, время и исходный ответ модели.

### 3.2. Инварианты

1. `needs_clarification => code=null, title=null, options>=2`.
2. До выбора специалиста неоднозначный запрос не может быть `ok` ни на одном backend.
3. Одинаковая позиция `(name, code)` в приложениях 2 и 3 сама по себе не является неоднозначностью.
4. Одно название с действительно разными кодами получает `multiple_codes`; оно не принимается
   автоматически. Форматные варианты кодов нормализуются только по утверждённому правилу.
5. Уточняющий признак в запросе (`грузовой`, `пожарный`, `для скорой`) отключает общий вопрос,
   если однозначно выбирает ветку.
6. Выбор опции не принимает произвольный code от клиента: сервер заново проверяет, что `option_id`
   принадлежит исходному запросу и той же версии каталога. При смене каталога — 409 и новое уточнение.
7. LLM-верификатор, `_best_answer`, head rescue и batch path не могут обойти ambiguity guard.
8. Выбор специалиста сохраняется отдельно от исходного ответа модели. Модельная уверенность не
   подменяется фиктивными 100%; UI пишет «выбрано специалистом», а eval исключает human-resolved
   ответы из калибровки модели.
9. Повторный выбор той же опции идемпотентен; два разных разрешения одной строки не теряются молча.

## 4. Работа A — уточнение неоднозначных запросов

### A1. Каталог интерпретаций и дедупликация

Создать `api/app/services/ambiguity.py` и версионируемый data/registry слой:

- нормализация названия, кода, `record_id`, приложения и procurement-признаков;
- объединение только действительно одинаковых интерпретаций;
- отдельные типы: `same_position_other_appendix`, `code_format_variant`, `true_multiple_codes`;
- построение смысловых веток по общему продуктовому слову и существующим леммам/мостам;
- аудит всех 87 многокодовых названий с протоколом решения специалиста.

### A2. Два комплементарных детектора, не hardcode «автомобиль»

1. **Generic data-driven guard для всех товарных групп.** Работает поверх уже полученного shortlist,
   поэтому не добавляет тяжёлый inference. Проверяет: общий/короткий запрос, несколько правдоподобных
   разных веток, отсутствие дискриминатора, абсолютную силу кандидатов и margin. Одинаковые дубли
   предварительно схлопываются, чтобы они не создавали ложную неоднозначность.
2. **Проверенный ambiguity registry для формулировки вопроса и покрытия синонимов.** Например:
   автомобиль, кран, мебель, светильник, компьютер, насос, счётчик, фильтр. Registry содержит только
   реальные позиции каталога, вопрос и различающие признаки; он не назначает ответ сам.

Точная родовая позиция (`игрушки` → «Игры и игрушки») имеет приоритет и остаётся обычным ответом.
Остаточная позиция «прочие» не используется как автоматическое оправдание произвольного выбора.
Пороговые значения настраиваются на dev-наборе и замораживаются до финального test-прогона.

### A3. Однокликовое разрешение

- Для single: `POST /classify/resolve` с исходным запросом, `option_id`, `catalog_sha256`.
- Для batch: `POST /classify/batch/{job_id}/items/{item_id}/resolve`.
- Сервер возвращает конкретную сохранённую позицию и источник, а не повторно угадывает свободный текст.
- В batch атомарно обновляется строка в SQLite/PostgreSQL; исходный результат и resolution audit
  остаются доступны. После разрешения сводка пересчитывается автоматически.

### A4. UI

Новый `ClarificationCard` в single и в строке batch:

- «Уточните, что именно закупается» вместо кода и процента;
- 2–6 осмысленных опций с названием, кодом и ссылкой на пункт;
- выбор одной кнопкой, состояние загрузки, ошибка без потери исходного вопроса;
- после выбора — код и пометка «Подтверждено специалистом»;
- кнопка «Изменить уточнение» с записью новой версии resolution, без подмены истории.

### A5. Набор качества

Добавить `eval/ambiguous_queries.csv` и `eval/ambiguity_eval.py`:

- положительные примеры из всех обнаруженных высокорисковых товарных семейств, не только транспорт;
- для каждого общего запроса минимум два конкретных control-запроса, которые должны классифицироваться;
- negative controls: точные родовые позиции, однозначные товары, товары вне перечня, опечатки,
  одинаковая позиция в разных приложениях;
- отдельный срез всех истинных многокодовых дублей;
- поля `expected_status`, допустимые `option_ids`, источник, reviewer, дата и обоснование;
- разделение dev/test по товарным семействам, чтобы проверка не запоминала конкретные слова.

## 5. Работа B — итоговый отчёт по закупке

### B1. Единый backend-сервис отчёта

Создать `api/app/services/procurement_report.py`. Он, а не разные функции в TS и Python, вычисляет
статус корзины, причины, риск и агрегаты. UI только отображает результат.

Основные взаимно исключающие buckets:

- `auto_accepted`: автоматический `ok` без блокирующих причин;
- `specialist_resolved`: позиция подтверждена/уточнена человеком;
- `needs_review`: все незакрытые риски, включая `needs_clarification`, `review`, многокодовость,
  исключение и сомнительную запись каталога;
- `not_found`: надёжное совпадение не найдено.

В UI можно показать три основные карточки из ТЗ: «Принято» = auto + specialist, «Требуют проверки»,
«Не найдено». При этом auto и specialist остаются отдельными числами в деталях. Инвариант:
`accepted + needs_review + not_found = total` после каждого изменения.

Причины — независимые flags, поэтому одна строка может иметь несколько причин, но входит только в
один основной bucket:

- `low_confidence`;
- `ambiguous_name`;
- `multiple_codes`;
- `catalog_review_required`;
- `code_exception`;
- `code_missing`;
- `conflicting_procurement_conditions`;
- `user_marked_incorrect`.

Отдельно показываются риски национального режима: запрет/ограничение/минимальная доля/неизвестно.
`not_found` никогда не превращается в «иностранный товар разрешён».

### B2. Приоритет проверки

Детерминированный `risk_rank` и сортировка:

1. пользователь отметил ошибку, истинные разные коды, исключение;
2. неоднозначное название;
3. отсутствие кода/сомнительная строка каталога/конфликт условий;
4. `not_found` с близкими кандидатами;
5. низкая уверенность — по возрастанию confidence;
6. остальные `not_found`.

Точные веса фиксируются в контракте и тестах, а не зависят от текущей сортировки таблицы.

### B3. Экран результатов

- Карточки сводки с числами и процентами; клик фильтрует таблицу.
- Фильтры «Только проблемные», по причине и по риску нацрежима.
- Сортировка «Сначала рискованные» по умолчанию для режима проверки, с сохранением исходного № строки.
- Панель причины прямо в строке: что случилось и какое действие нужно.
- Быстрый переход к следующей нерешённой позиции и счётчик оставшихся.

### B4. Экспорт

XLSX:

1. `Сводка` — счётчики, причины, нацрежим, имя файла, дата, report id, catalog/model versions;
2. `Требуют проверки` — только рискованные строки, уже отсортированные по `risk_rank`;
3. `Все позиции` — исходный и текущий результат, причина, confidence, source, resolution;
4. `Метаданные` — срок хранения, дисклеймер и provenance.

CSV содержит те же машинные поля, включая `item_id`, исходный №, `attention_reasons`, `risk_rank`,
текущий/исходный код и `decision_source`. Числа на экране, XLSX и CSV проверяются на идентичность.
Сохраняется существующая защита CSV от formula injection.

### B5. Сохранение и возврат

Не создаём вторую несогласованную базу: используем существующий job store как snapshot отчёта.

- Alembic-миграция добавляет metadata: filename, created_at, catalog/model revision и retention.
- Для SQLite зеркалятся те же поля.
- Готовый отчёт получает отдельный настраиваемый срок `REPORT_TTL_DAYS=30`; срок виден пользователю.
  Это не «вечная история» и не скрытое хранение.
- `GET /classify/batch/{job_id}` дополняется summary/metadata либо выделяется тонкий
  `GET /reports/{job_id}` над тем же store.
- В `localStorage` сохраняются только report id и имя файла, **не названия товаров**. При reload
  running job докатывается, completed report загружается с сервера. Старый запрет восстановления
  завершённых результатов удаляется вместе с его тестами.
- После выбора уточнения обновлённый результат сохраняется на сервере и восстанавливается после
  reload и рестарта Docker. Просроченный отчёт даёт честное 404/сообщение, а не пустой экран.
- Общая серверная история и аккаунты в объём не входят.

## 6. Роли и зоны ответственности

| Роль | Конкретные задачи | Результат |
| --- | --- | --- |
| **PO / владелец решения** | Зафиксировать четыре состояния, bucket-правила, risk precedence, срок хранения, сценарий демо; не давать ML подменять продуктовые решения порогами | Подписанная decision table и acceptance criteria |
| **Domain expert / закупщик-юрист** | Разметить неоднозначности и контрольные запросы; классифицировать 87 многокодовых названий; решить правила exception/codeless; зафиксировать редакцию ПП и по возможности 41 `unclear`; разметить приоритетную часть реальных 400 | Верифицированный gold set и протокол спорных решений |
| **ML/NLP-инженер** | Дедупликация интерпретаций, ambiguity registry + generic guard, интеграция с catalog и qdrant, запрет обхода через LLM/variants/rescue, eval и анализ false clarification | Детерминированный guard с измеренным recall/false-positive rate |
| **Backend-инженер** | Контракт 2.0, resolve API, `item_id`, report service, риски/агрегаты, store/atomic resolution, миграция, retention, CSV и API | Сквозной сохранённый API без противоречий между single/batch |
| **Frontend-инженер** | ClarificationCard, dashboard, фильтры/риски, однокликовое уточнение, XLSX, восстановление completed report, mobile/a11y | Полный пользовательский сценарий A+B |
| **QA / MLOps** | Контрактные/property/integration/e2e-тесты, строгие метрики, PostgreSQL/SQLite, reload/restart, E5+TF-IDF, latency, CI, Docker smoke и evidence pack | Воспроизводимое доказательство качества и запуск одной командой |

Если людей меньше: PO и domain могут быть одним человеком, backend и ML — вторым, frontend — третьим,
но **финальную разметку нельзя назначать ответам самой модели**.

## 7. Последовательность и параллельность

Оценка: 8–10 рабочих дней командой из 4–6 человек; при 2–3 исполнителях — примерно 12–15 дней.

### Этап 0. Зафиксировать базу — 0,5–1 день

- Сохранить текущие E5/TF-IDF отчёты, acceptance и список опасных запросов.
- PO и domain выпускают decision table: статусы, дубли, исключения, bucket/risk rules.
- QA добавляет строгий baseline, где одинаковый title не засчитывает другой код.

### Этап 1. Контракт и данные — 1–2 дня

- Backend публикует схему 2.0 и тестовые fixtures; frontend параллельно строит UI на mock.
- ML и domain формируют ambiguity dev/test и реестр многокодовых названий.
- Backend готовит миграцию metadata/report store.

**Gate:** команда согласна, что такое неоднозначность и какая строка считается принятой. Без этого
не начинать подгонку порогов.

### Этап 2. Сквозная задача A — 2–3 дня

- ML реализует guard; backend — resolve; frontend — однокликовый выбор.
- Сначала mini-catalog unit tests, затем TF-IDF и полный E5.
- Single и batch идут через один и тот же resolver и контракт.

**Gate:** `автомобиль` не выдаёт код до выбора, `автомобиль грузовой/легковой` не сломаны,
выбор восстанавливается после reload.

### Этап 3. Сквозная задача B — 2–3 дня, параллельно с A после фиксации контракта

- Backend считает summary/reasons/risk и сохраняет отчёт.
- Frontend делает карточки, фильтры, risk sort, XLSX/CSV и восстановление.
- QA проверяет пересчёт после каждого уточнения и тождественность экспорта экрану.

**Gate:** смешанная закупка показывает корректную сводку, проблемная строка доступна в один клик,
отчёт переживает reload и рестарт.

### Этап 4. Доказательное качество — 1–2 дня

- Прогнать новые и старые наборы на обоих реальных режимах; проверить latency и Docker.
- Разобрать каждый false confident/false clarification; не скрывать изменение покрытия.
- Завершить приоритетную предметную разметку реальных запросов и редакции источника.

### Этап 5. Сдача — 1 день

- Чистая сборка с нуля, миграция на старом volume, backup/restore.
- Обновить README, API contract, retention/privacy, eval и ограничения.
- Записать демо и приложить machine-readable acceptance report.

## 8. Definition of Done и числовые gate'ы

### Неоднозначность

- **0 уверенных `ok` и 0 навязанных кодов** на размеченном ambiguous test до уточнения.
- `needs_clarification` recall ≥95% на экспертном test; все найденные исключения разобраны явно.
- Ложное уточнение на однозначных control-запросах ≤1%; отдельно показать число строк, не только %.
- 100% валидных выборов возвращают именно выбранную позицию; чужой `option_id` и старый catalog hash
  отклоняются; повтор идемпотентен.
- На прежних однозначных наборах нет регресса top-1/top-3/верной тишины сверх существующего gate.
  Перевод ambiguous строк из `ok` в уточнение — желаемое изменение, а не «падение coverage».

### Отчёт

- Property test: buckets всегда взаимно исключающие и сумма равна total; reason counts могут пересекаться.
- Экран = API = XLSX = CSV по каждой строке и агрегату.
- После уточнения bucket, риск, экспорт и сохранённая версия меняются атомарно.
- Reload, закрытие/открытие браузера и `docker compose restart api worker` сохраняют отчёт и выбор.
- Истёкший retention обрабатывается явно; никакого молчаливого показа чужого/устаревшего отчёта.

### Инженерия

- Все backend/frontend/contract/store/e2e/a11y проверки зелёные; добавлены PostgreSQL и SQLite кейсы.
- `docker compose up --build` работает с нуля и на существующем volume.
- Полный E5 + Qdrant + PostgreSQL + Celery acceptance повторён; TF-IDF остаётся лёгким CI-контуром,
  но не подменяет E5-результат.
- Сохраняются исходные ограничения: одиночный запрос <5 с, batch 100 <120 с. Guard работает на
  существующем shortlist и не добавляет внешний вызов.

## 9. Что показывать жюри

Демонстрационный файл из 8–10 строк: однозначный ноутбук, `автомобиль`, `автомобиль грузовой`,
`кран`, `мебель`, товар вне перечня, низкоуверенный товар, истинный многокодовый дубль и обычный
дубль между приложениями.

Сценарий за 3–4 минуты:

1. Показать старую ловушку: общий «автомобиль» раньше становился пожарным с 81,75%.
2. Загрузить файл: сводка сразу показывает принятые/проверяемые/не найденные.
3. Нажать «Требуют проверки»: первые — самые рискованные, у каждой причина.
4. У «автомобиля» нет итогового кода; выбрать «легковой» одним действием → код + источник,
   `decision_source=specialist`, сводка пересчиталась.
5. Открыть многокодовую строку и показать, что система не маскирует её под обычную альтернативу.
6. Скачать XLSX: листы «Сводка» и «Требуют проверки» уже готовы для работы специалиста.
7. Перезагрузить страницу и перезапустить контейнеры: отчёт и выбор на месте.
8. Финальный кадр: полный E5 readiness, зелёный CI, строгие метрики и честные ограничения.

## 10. Приоритеты и сознательные отказа

### P0 — необходимо для победы по выбранной номинации

- Новое состояние неоднозначности, отсутствие кода до выбора, однокликовый resolver.
- Generic guard + registry, оба backend, batch и single.
- Экспертный ambiguity/duplicate eval и строгие метрики.
- Сводка, причины, риск, фильтры, XLSX/CSV, сохранение completed report и resolution.

### P1 — сильно повышает доверие

- Разметка приоритетной части 400 реальных запросов, решение DA-5/DA-2/DA-6.
- Метрики clarification/resolve/report restore в Prometheus и audit resolution history.
- Миграция старого volume, восстановление backup, полный E5 evidence pack.

### Не делаем в этом этапе

- Новый кросс-энкодер/BGE/более крупную LLM ради «технологичности».
- Обучение top-1 на неоднозначных запросах как будто у них один эталон.
- Поднятие/понижение confidence для маскировки проблемы.
- Hardcode только автомобиля или только списка из PDF.
- Автоматический выбор уточнения LLM.
- Аккаунты, глобальную историю, новую очередь/БД и переписывание работающего retrieval.
- Заявления «актуальная нормативная база» и «точность на реальных запросах» без экспертных данных.

## 11. Главные риски

| Риск | Как контролируем |
| --- | --- |
| Guard задаёт слишком много вопросов и снижает полезность | Negative controls, false-clarification gate, точные родовые позиции и конкретные запросы |
| Guard пропускает новую товарную группу | Data-driven обнаружение веток, registry только как усиление, разбиение test по семействам |
| Многокодовые дубли скрыты старой метрикой | Строгий code+position eval, отдельный duplicate slice, запрет same-title shortcut |
| UI и backend по-разному считают риск | Единый report service и общие fixtures; TS не дублирует юридические выводы |
| Возврат отчёта нарушает прежнее privacy-решение | В браузере только id, серверный TTL и явное сообщение; никакой локальной истории названий |
| Побочный обход через варианты запроса/LLM/head rescue | Общий post-decision guard и инвариантные тесты на все пути |
| После обновления каталога старая опция указывает не туда | catalog hash + server-side option validation + 409 |
| Красивый процент вместо реальной верности | Строгие row-level результаты, отдельные auto/human buckets, публикация ошибок и ограничений |
