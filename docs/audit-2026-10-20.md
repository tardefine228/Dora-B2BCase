### 3.2 Сравнение с `main` — это не «улучшение», а сдвиг по фронту

`main` (пересобранный на тех же данных, воспроизводится точно):

**Как читать.** Ветка лучше на низкой тишине (до ~88%): она отвечает на большее число товаров из перечня.
`main` лучше на высокой тишине (≥90%): при «молчании» 94% он даёт 130 верных ответов против 124–127 у ветки.
Ни одна из веток не доминирует — это **продуктовое решение**, а не техническая регрессия.
Проблема в том, что решение принято молча: код (`REVIEW_CONFIDENCE_FLOOR = 0.13`, `ml/train_reranker.py:658`)
говорит одно, CI-гейт (≥80% тишины, `.github/workflows/lint.yml:84`) — другое, README — третье (81.5%).
Сейчас не выполняется ни одно из трёх.

### 3.3 Где теряются коды

Для 166 запросов с эталонным кодом измерено независимо:

| Ступень | Результат | Что это значит |
| --- | ---: | --- |
| правильный код в лексическом шорт-листе (top-25) | **162 / 166 = 97.6%** | потолок поиска почти выбран |
| правильный код в dense top-8 (tfidf) | 142 / 166 = 85.5% | векторный поиск **слабее** лексики как генератор кандидатов |

Отсюда: **резерв качества — в реранкере, порогах и доменных правилах, а не в эмбеддере.**
Идеальный эмбеддер может добавить максимум 4 строки из 166 (+2.4 п.п.) — и только если он найдёт те 4,
которые лексика не находит вообще («Счетчик воды крыльчатый», «Автоцистерна для перевозки молока»,
«Судно прогулочное», «Шкаф металлический для документов», «Нетканое полотно»).

### 3.5 Векторный слой: измерено «ноль»

- В `ml/artifacts/reranker.json`: `dense_cosine = 0.0`, `dense_gap = 0.0`, `top_dense_cosine = 0.0`,
  `top_dense_gap = 0.0`, `query_dense_top = 0.0`. Модель обучена **без** векторов.
- Включение и выключение `VECTOR_SEARCH` на 274 строках: **0 изменений кода, 0 изменений статуса**,
  4 строки сдвинули `confidence_raw` на 0.001–0.02.
- Причина: кандидат, найденный только векторами, приходит в реранкер с `lexical_score ≈ 0` и нулевым dense-весом,
  поэтому не может выиграть. Векторы расширяют шорт-лист, но не участвуют в решении.

**Вывод:** сегодня «векторный поиск» — это стоимость (~0,5 ГБ весов + torch, +10 мин сборки, RAM, cold start) без эффекта.
Либо его надо довести до конца (см. §7), либо честно выключить по умолчанию.

### 3.6 Дыра в контракте: `status="ok"` без кода

Шесть позиций приложения 4 («Не указан») не имеют ОКПД2. Они попадают в индекс и могут стать top-1:

```text
'Мочеприемники и калоприемники'
  -> code=None, status=ok, confidence=0.944, title='Мочеприемники и калоприемники'
```

Контракт v1.0 говорит: «`code` — `null` при `not_found`», но обратного инварианта («`code=null` ⇒ `not_found`»)
нет ни в документах, ни в тестах. UI в этом случае покажет «—» рядом с бейджем «Уверенный результат».
Это надо либо запретить в схеме, либо явно описать как отдельный случай.

**Ещё две находки в данных, которые влияют на юридическую корректность:**

- строка `2-454-02` «Сыры, продукты сырные и творог» имеет `code_role = «Исключение»`, но участвует в выдаче
  как обычная позиция: «Творог 5%» получает `10.51.4` с уверенностью 0.43. Для перечня с исключениями это
  опасная подсказка — нужен либо флаг в ответе, либо исключение таких строк из индекса (`ACTIVE_CODE_ROLES`
  в `ml/catalog_loader.py` сейчас пуст и не фильтрует ничего);
- 129 строк имеют `review_required = True` (сомнения OCR на этапе парсинга), и этот флаг нигде не используется:
  потенциально искажённое название или код уходит в ответ как обычный.

## 6. Что делать параллельно: 4 недели, три дорожки

```
Неделя 1   [A] PO-1 → BE-3 → ML-1 → OPS-1   (политика + гейт + CI)
           [B] DA-1 (реальный набор)  ||  [C] OPS-2, OPS-3 (проверка образа)
Неделя 2   [A] ML-2 (dense на e5)  → ML-3 (правила FP)
           [B] DA-2, DA-3 (спорные + каталог) || [C] FE-1, FE-2 (feedback UI) + BE-2
Неделя 3   [A] ML-5 (recall на реальных) → решение по эмбеддеру (см. §7)
           [B] DA-4, DA-5 || [C] FE-3, FE-4, FE-5, OPS-4
Неделя 4   [A] ML-4 (hard negatives) / ML-6 (кросс-энкодер, если recall низкий)
           [B] реестр мостов + приёмка каталога || [C] BE-5, BE-6, OPS-5..7, QA-1..3
```

**Правила параллельности:**

- Дорожка **B (данные)** — узкое место для всех ML-улучшений. Её надо запускать в день 1; без реальной разметки
  любые решения по модели — гадание.
- Дорожка **C (frontend/ops)** не зависит от ML и даёт видимый результат пользователю (кнопки вердикта, загрузка PDF,
  скорость UI) — её можно вести отдельным человеком.
- Дорожка **A** последовательна внутри себя: политика → гейт → dense-признаки → правила.
- Не менять пороги и признаки без пересборки модели + `--sweep` + записи в `eval/experiments.md` (правило уже есть
  в `docs/next-steps.md`, его надо соблюдать).

## 7. Нужно ли загружать BGE-3? Решение

### 7.1 Терминология

Публичного открытого релиза под именем **«BGE-3»** в доступных источниках не видно: BAAI ведёт линейку
**BGE-M3** (568M параметров, 1024 измерения, контекст 8192, MIT) и специализированные варианты
(`bge-m3-unsupervised`, `USER-BGE-M3` — русско-адаптированная версия на 359M). Обзор августа 2026 прямо пишет,
что новых general-purpose текстовых эмбеддеров у BAAI после июля 2024 не выходило.
Поэтому ниже рассматривается **BGE-M3** (и, где это важно, русско-адаптированный `USER-BGE-M3`).
Если в команде обсуждается другой файл/чекпоинт — пришлите точное имя, но вывод не изменится: он основан не на
качестве модели, а на архитектуре вашего пайплайна.

### 7.2 Шесть фактов, которые определяют ответ

1. **Векторный сигнал сегодня не доходит до решения.** Веса dense-признаков в отгруженной модели — 0.0.
   Включение/выключение векторного поиска: 0 изменений кодов и статусов на 274 строках. Любая модель, хоть bge-m3,
   хоть идеальная, **сегодня даст ровно ноль**.
2. **Потолок поиска почти выбран.** Правильная позиция уже в лексическом top-25 для **97.6%** запросов с кодом.
   Лучший эмбеддер может добавить максимум **~4 строки (+2.4 п.п.)**, а не «вылечить распознавание».
3. **Слабое место — ложные подсказки, а не недонайденные коды.** 30 ложных подсказок из 108; 5 из них имеют
   сырую уверенность ≥0.5. Эмбеддер такие пары, наоборот, **усиливает** (семантически «робот-пылесос» и
   «промышленные роботы» близки). Эксп. 15 в репозитории это уже показал: семантика гасит 2 ложные подсказки из 13
   и добавляет регрессии.
4. **Семантика полезна, но небольшим выигрышем при правильной интеграции.** Переобучение с dense-признаками
   (даже на слабом tfidf) дало **+1.9 п.п. top-1** и **+2…3 верных подсказки при равной тишине**
   (138 против 135 при 86%). Это аргумент за *интеграцию*, а не за *большую модель*.
5. **Цена BGE-M3 на вашем железе существенна.** 568M против 118M у e5-small: ~2.3 ГБ весов в fp32,
   RSS API ≥3–4 ГБ (сейчас лимит 2 ГБ в compose и 1 ГБ в `.env.example`), латентность на CPU в 3–5× выше
   (в экспериментах репозитория семантический режим: p50 171 мс против 38.5 мс у каталогового),
   cold start +20–40 с, образ +~1.8 ГБ. По независимым замерам bge-m3 на CPU — единицы-десятки мс на короткий текст,
   но в связке с torch и вашим лимитом памяти это уже не «бесплатно».
6. **Метрика, на которой надо сравнивать, ещё не готова.** Размеченный набор производен от каталога (запросы — это
   названия позиций и их обрезки), реальные 100 запросов не в репозитории, обратной связи нет.
   На таком наборе bge-m3 будет выглядеть так же, как e5: ±1–2 п.п., в пределах шума.

### 7.3 Вердикт

> **Не загружать BGE-3/BGE-M3 сейчас. Не как «улучшение распознавания» и не как замену e5-small.**
>
> Причина не в модели: в текущем пайплайне её сигнал не участвует в решении (вес 0), потолок поиска почти выбран
> (97.6%), а главная проблема — ложные подсказки вне перечня, которые семантика не лечит и частично усиливает.
> Загрузка bge-m3 сегодня даст **измеримый ноль качества** и ощутимый минус по латентности, памяти и сложности сборки.

**Ответ меняется на «да», когда выполнены все четыре условия:**

1. dense-признаки доведены до решения и измерены на e5-small (ML-2) — то есть механика уже работает;
2. есть **≥300–500 реальных размеченных запросов** с вердиктами специалистов (DA-1 + BE-2), а не производные от каталога;
3. на этих реальных запросах **лексический recall@25 < 90%** (ML-5) — то есть поиск действительно не находит;
4. есть железо: API ≥4 ГБ RAM (или GPU), и это подтверждено замером на целевой машине (OPS-2).

Если хотя бы одно условие не выполнено — сначала закрывайте его, а не покупайте модель.

### 7.4 Если всё-таки берём: как добавить правильно

```bash
# 1. Скачать модель в локальный каталог (на машине с доступом к huggingface.co)
python scripts/download_model.py BAAI/bge-m3 ./models/bge-m3

# 2. Собрать образ с явно заданной моделью и БЕЗ права на тихую деградацию
EMBEDDER_MODEL=BAAI/bge-m3 INSTALL_TRANSFORMER=true docker compose build

# 3. Проверить, что загрузилась именно она (а не spaCy)
docker compose exec api python -c \
  "from ml.embedder import get_encoder; e=get_encoder(); print(e.tag, e.dim)"   # st-bge-m3 1024
curl -s localhost:8000/health/ready | python -m json.tool    # vector_search.embedder = st-bge-m3, dim = 1024

# 4. Пересобрать артефакт реранкера ПОД ЭТОТ эмбеддер (иначе он останется лексическим)
docker compose exec api python scripts/build_model.py --dense --models-dir /app/ml/artifacts
#    -> ml/artifacts/reranker.st-bge-m3.json — артефакты несовместимы между эмбеддерами, это уже реализовано

# 5. Снять метрики и свип порогов ДО включения в прод
PYTHONPATH=api python eval/run_eval.py --sweep
PYTHONPATH=api python eval/threshold_sweep.py --backend catalog

# 6. (опционально) семантический режим как второй бэкенд
ML_ENABLED=true CLASSIFIER_BACKEND=qdrant docker compose up -d
curl -X POST localhost:8000/admin/reindex -H "X-Admin-API-Key: $ADMIN_API_KEY"
```

Обязательные технические детали:

- **Память:** `api` и `worker` — 4 ГБ; `MODEL_BATCH_SIZE=8`; ограничить `max_seq_length` до 256–512
  (названия товаров короткие, 8192 контекста не нужны и только жгут память).
- **Тег эмбеддера** уже участвует в имени коллекции Qdrant и в имени артефакта реранкера — не смешивать.
- **Не использовать `EMBEDDER_BACKEND=auto` в проде:** фиксированный `sentence-transformers`, чтобы падение
  загрузки было ошибкой, а не тихим откатом на spaCy.
- **Пороги** для новой шкалы снять отдельно (`QDRANT_*_FLOOR` / `CATALOG_*_FLOOR`), не наследовать от e5.
- **Откат:** старый артефакт и старая коллекция остаются на месте; переключение — переменными окружения.
- BGE-M3 **не требует префиксов** `query:`/`passage:` (в отличие от e5) — код уже это учитывает (`_e5_prefixes`).

### 7.5 Как дообучать «до лучшего распознавания»

Приоритет по соотношению «эффект / цена»:

1. **Реранкер (уже есть, дёшево).** Обучение на реальных вердиктах + hard negatives. Именно здесь основной резерв:
   правильный код уже в шорт-листе в 97.6% случаев, но не всегда первый. Никакого GPU не нужно.
2. **Кросс-энкодер на top-10 (средняя цена).** Небольшая русская модель (rubert-tiny2 ~29M или RuBERT-base ~178M)
   или `bge-reranker-v2-m3` (568M — на CPU дорого). Даёт обычно больше, чем замена би-энкодера, но добавляет
   10 forward-проходов на запрос. Пилот обязателен с замером p95.
3. **Дообучение самого эмбеддера (дорого, последним).** Contrastive (MultipleNegativesRankingLoss) на парах
   «запрос → название позиции», 2–5 тыс. пар минимум, hard negatives из BM25 top-10 без позитива, 1–3 эпохи,
   заморозка нижних слоёв или LoRA. Обязательно: отдельный held-out, пересчёт калибровки Платта и порогов,
   проверка на «тишину». Ожидание: +1–3 п.п. top-1 — то есть сопоставимо с п.1, но в разы дороже.
   Риск: переобучение на формулировки каталога и потеря обобщения на бытовые названия.
4. **Fine-tune не нужен, если** на реальных запросах recall@25 ≥ 90%: узкое место не в эмбеддере.

### 7.6 Чем компенсировать, если не берём (и почему это сработает)

| Мера | Ожидаемый эффект (измерено/оценено) | Почему сработает |
| --- | --- | --- |
| Порог `review` 0.13 → 0.22–0.25 | тишина **72.2% → 84–87%**, цена: 7–10 верных подсказок | прямая перестановка рабочей точки; цифры в §3.1 |
| `not_found` + альтернативы (вместо кода) | метрики те же, но специалист видит кандидатов | контракт это уже поддерживает: `alternatives` заполняются и при `not_found` |
| Парные запреты для 5 «уверенных» ложных друзей | тишина **+4…5 п.п.** без потери верных | порог их не убирает (raw ≥ 0.5), а правило пары — убирает |
| Dense-признаки на e5-small (уже в образе) | **+1.9 п.п.** top-1; **+2…3** верных при равной тишине | эксперимент §3.5; механика уже написана, нужен только гейт и порог |
| Hard negatives из реальных вердиктов | самый большой и долгий резерв: обычно +3…8 п.п. на живом трафике | учим модель именно на тех ошибках, которые видит пользователь |
| Кросс-энкодер на top-10 | +2…4 п.п. top-1 при приемлемой латентности (пилот) | второй проход «запрос × кандидат» видит оба текста одновременно |
| Чистка каталога (дубли, длинные названия, OCR) | +0.5…1.5 п.п. | длинные названия размывают признаки; дубли искажают margin |

**Итог по компенсации:** да, компенсировать получится — и с запасом по сравнению с заменой эмбеддера.
Реалистичная цель без bge: **топ-1 83–86% при тишине 85–88%** (сейчас: 87.3% при 72.2%).
С bge-m3 без всех остальных мер — те же 87% и 72%, только медленнее.

### 7.7 Эксперимент, который закрывает вопрос окончательно

**Дизайн:** A/B на одном и том же коде и одном наборе, три конфигурации:
`lexical` (сейчас), `lexical + e5-small dense`, `lexical + bge-m3 dense` (или `USER-BGE-M3`).
Набор: `eval/real_queries.csv` (≥300 реальных запросов, ≥100 «вне перечня»), разметка эксперта.

**Метрики (все четыре обязательны):**

| Метрика | Порог успеха bge |
| --- | --- |
| top-1 по товарам из перечня при фиксированной тишине | ≥ +2 п.п. к e5-small |
| точность «тишины» вне перечня | не ниже, чем у e5-small |
| p95 латентности `/classify` на целевой машине | ≤ 250 мс |
| RSS API | ≤ 80% лимита машины |

**Правило решения:** если хотя бы одна метрика не проходит — bge-m3 отклоняется, выигрыш фиксируется на реранкере
и данных. Если проходит — bge-m3 включается как **второй** артефакт (`reranker.st-bge-m3.json`), а не вместо e5,
и только после этого обсуждается смена дефолта.

**Стоимость эксперимента:** ~3–5 человеко-дней (загрузка модели, пересборка артефактов, два прогона, замер).
**Стоимость ошибки без эксперимента:** +2.3 ГБ модели, +30 с cold start, ×3–5 латентности и ложное чувство,
что «распознавание улучшилось».
